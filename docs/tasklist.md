## Этап 1 — ядро бэкенда

- [x] **T1.1 Аутентификация**
  Регистрация, вход, refresh, logout; argon2, JWT access 15 мин в теле ответа +
  refresh 30 дней в httpOnly cookie с ротацией через `refresh_sessions`
  ([ADR-0008](adr/0008-session-storage.md), §3.1 [data-model.md](data-model.md)).
  Политика пароля — §5.1 [data-model.md](data-model.md): 12–128 символов, без правил
  состава, блок-лист top-10000. Хэширование argon2 выносится в поток
  (`anyio.to_thread`), иначе вход блокирует event loop (§12.5 conventions.md).
  *проверка:* pytest — успешный вход; неверный пароль → 401; повторная регистрация → 409;
  протухший access → 401; refresh по cookie без тела выдаёт новый access; повторное
  использование ротированного refresh → 401 и сессия закрыта; logout делает cookie
  непригодной; пароль из блок-листа и пароль короче 12 символов → 422; пароль
  в 100 символов с пробелами принимается; в логах есть `user.login.failed` с причиной
  и **без email**, `auth.refresh.reuse_detected` уровня ERROR при повторном
  использовании токена; 11-я попытка логина с одного IP → 429
  с `Retry-After`; 6-я неудачная попытка по одному email → 429 даже с другого IP
  (§9.2 [vision.md](vision.md)).

- [x] **T1.2 Проекты**
  CRUD включая `DELETE` (каскад), генерация `public_key`, `allowed_origins`, `theme`
  со значениями по умолчанию, лимиты из §5 [data-model.md](data-model.md), эндпоинт
  `snippet`. Списковый ответ — в конверте `{items, next_cursor}` (§12.8 conventions.md).
  **Зависимость `get_owned_project` создаётся здесь и используется с первого маршрута** —
  изоляция не дописывается потом, иначе первый же забытый обработчик станет утечкой.
  *проверка:* pytest — CRUD; `public_key` уникален; дефолтная тема присутствует в ответе;
  пустой `allowed_origins` → публичный конфиг отвечает отказом (fail closed);
  11-й проект на пользователя → 422.

- [x] **T1.3 Изоляция арендаторов: матрица проверок**
  Зависимости созданы в T1.2 и T1.4; здесь — полная матрица тестов и запрет прямого
  `session.get` в обработчиках панели (проверяется ревью диффа и grep в тесте).
  *проверка:* pytest — матрица 2 пользователя × 2 проекта × все приватные маршруты;
  чужой объект → 404 (не 403, не 200).

- [x] **T1.4 Туры**
  CRUD, `publish`/`unpublish`, валидация `url_match` (включая проверку regex на
  компилируемость и запрет катастрофического бэктрекинга простым лимитом длины);
  `GET /tours/{id}` отдаёт тур со шагами; список туров проекта возвращает `runs_7d`
  и `completion_rate_7d` одним агрегатом (§6 [screens.md](screens.md)).
  *проверка:* pytest — публикация меняет статус и `published_at`; невалидный regex → 422;
  публикация тура без шагов → 422; архивный тур не попадает в публичный конфиг;
  список из 3 туров отдаётся одним запросом с метриками; тест на число SQL-запросов
  фиксирует константу — N+1 не проходит (§12.6 conventions.md).

- [x] **T1.5 Шаги**
  CRUD + изменение порядка одним `UPDATE ... CASE` (уникальность объявлена
  `DEFERRABLE`, §3.2 [data-model.md](data-model.md)); удаление последнего шага
  опубликованного тура снимает тур с публикации и возвращает новый статус (§8.2
  [vision.md](vision.md)).
  *проверка:* pytest — после `PUT /steps/order` позиции 0..N−1 без дыр и дублей;
  перестановка шага с 3-й позиции на 1-ю проходит одним оператором;
  два конкурентных reorder одного тура не нарушают уникальность.

- [x] **T1.6 Сниппет установки**
  `GET /projects/{id}/snippet` — готовый тег со `data-key` и `data-api`.
  *проверка:* pytest — ответ содержит актуальный `public_key` и адрес API из настроек.

## Этап 4 — аналитика

- [ ] **T4.1 Приём событий**
  Миграция 003 (§3.3 [data-model.md](data-model.md)) и `POST /public/events`: батч
  одним `INSERT ... ON CONFLICT` без предварительного `SELECT` (§12.7 conventions.md),
  валидация, проверка `Origin` против `allowed_origins`, идемпотентность по `event_id`,
  обрезка URL до path, лимиты по §9.2 [vision.md](vision.md) за интерфейсом
  `RateLimiter` (in-memory реализация), 429 с `Retry-After` при превышении,
  всегда 204 при валидном ключе и соблюдённом лимите.
  *проверка:* pytest — двойная отправка одного батча → одна строка в БД; чужой Origin
  → 403; битая схема события → 204 и событие отброшено (виджет не ретраит).

- [ ] **T4.2 Отправка событий из виджета**
  Буфер, флаш по таймеру и размеру, `sendBeacon` на `visibilitychange`, повтор из
  localStorage; `device` определяется через `matchMedia`, User-Agent не разбирается
  (§7.1 [vision.md](vision.md)).
  *проверка:* e2e — закрытие вкладки посреди тура доставляет `tour_started` и
  `step_viewed`; при недоступном API события уходят при следующей загрузке; на 429
  отправка повторяется с экспоненциальной задержкой, события не теряются.

- [ ] **T4.3 Агрегация**
  `GET /tours/{id}/analytics?range=7d|30d` — тоталы, воронка по шагам, drop-off,
  проблемные шаги, скользящее окно в UTC.
  *проверка:* pytest на фикстуре из 10 прогонов (3 завершения, 5 скипов, 2 обрыва) —
  все числа совпадают с посчитанными вручную по формулам §7.2 vision.md; событие
  старше окна в выборку не попадает; тоталы и воронка считаются по одной границе.

- [ ] **T4.4 Экран воронки**
  Четыре тотала, воронка по шагам, подсветка худшего шага, блок «Проблемы».
  *проверка:* e2e — после 10 прогонов на стенде числа в UI совпадают с ожидаемыми.

## Замечания

Сюда попадает всё, что замечено по пути, но не входит в текущую задачу: несвязанные
проблемы, долги, идеи. Не правим молча — записываем.

- **Маршруты аутентификации не пишут `rate_limit.exceeded`.** Журнал §9.3 vision.md
  требует запись при превышении лимита; `_check` в `api/v1/panel/auth.py` только
  поднимает 429. В публичном конфиге запись есть (T2.1). Чинить вместе с третьим
  потребителем лимитера — тогда же общий помощник переедет в `core/rate_limit.py`.
- **У типа события `widget_ping` нет отправителя.** Статус «виджет подключён»
  считается по `widget_last_seen_at`, который обновляет сам запрос конфига — отдельный
  запрос с сайта клиента на каждую загрузку страницы ради тех же данных был бы
  лишним. Решить в T4.1: либо тип убирается из перечисления миграцией, либо
  начинает отправляться с какой-то отдельной целью.
- ~~**Ошибки самого FastAPI не в формате RFC 9457.**~~ Закрыто в T1.1: добавлены
  обработчики `StarletteHTTPException` и `RequestValidationError`; 404, 405 и 422
  отдаются как `application/problem+json`, значения полей в ответ не попадают.
  Проверяется `tests/test_error_format.py`.
