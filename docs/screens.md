# Экраны панели и контракт с API

Версия: 1.0 · Дата: 2026-10-13

Что реализуем на фронтенде, какие эндпоинты каждый экран вызывает, какие данные
показывает. Документ существует ради сверки: **не должно быть экрана без эндпоинтов и
эндпоинта без потребителя.** Результаты этой сверки — §6, она уже изменила контракт API.

Границы: только панель владельца. Виджет экранов не имеет, его контракт — §8.1
[vision.md](vision.md); макеты и раскладка — §4.3 и §4.6 там же; поля и типы —
[data-model.md](data-model.md).

---

## 1. Карта маршрутов

```
/                                   → редирект на /projects
/login, /register                   публичные
/projects                           список проектов
/projects/:id/install               установка виджета
/projects/:id/tours                 список туров
/projects/:id/tours/:tid            конструктор тура
/projects/:id/tours/:tid/analytics  воронка
/projects/:id/branding              тема оформления
*                                   404
```

Всё, кроме `/login` и `/register`, — внутри `ProtectedRoute` и `AppLayout`.

## 2. Общие элементы

### S0. Восстановление сессии (не маршрут)

| | |
|---|---|
| Когда | при старте приложения и при F5 |
| Запросы | `POST /v1/auth/refresh` (по cookie), затем `GET /v1/me` |
| Данные | `email` владельца для шапки |
| Состояния | до ответа — сплэш, **не** экран логина ([ADR-0008](adr/0008-session-storage.md)); 401 → `/login` |

### S1. AppLayout — шапка для всех приватных экранов

| | |
|---|---|
| Запросы | `GET /v1/projects` (для переключателя) |
| Данные | список `{id, name}`, email владельца — из `AuthProvider` |
| Мутации | `POST /v1/auth/logout` → очистка кэша Query и переход на `/login` |
| Ключи Query | `['projects']` |

Почта берётся из провайдера, а не запрашивается заново: восстанавливая сессию (S0),
он уже сделал `GET /v1/me`. Второй запрос тем же экраном был бы лишним (T3.1).

## 3. Экраны аутентификации

### S2. `/register`

| | |
|---|---|
| Назначение | создать аккаунт |
| Поля формы | email, пароль |
| Мутации | `POST /v1/auth/register` → `{access_token, expires_in}` + cookie |
| Ответы | 409 — email занят; 422 — слабый пароль или некорректный email |
| Переход | успех → `/projects` |

### S3. `/login`

| | |
|---|---|
| Мутации | `POST /v1/auth/login` |
| Ответы | 401 — неверная пара email/пароль (без уточнения, что именно неверно) |
| Переход | успех → страница, с которой пришёл редирект, иначе `/projects` |

Ссылки «забыли пароль?» нет: сброс пароля вне границ MVP (§1.1 [idea.md](idea.md)).
Экрана смены пароля в кабинете тоже нет — там же.

## 4. Экраны проекта

### S4. `/projects` — список проектов

| | |
|---|---|
| Запросы при входе | `GET /v1/projects` |
| Отображает | `name`, статус подключения виджета (из `widget_last_seen_at`), число туров |
| Мутации | `POST /v1/projects` (создать: только `name`), `DELETE /v1/projects/{id}` |
| Ключи Query | `['projects']` |
| Состояния | пусто → приглашение создать первый проект; это же первый экран после регистрации |
| Переходы | карточка → `/projects/:id/tours`; «Установка» → `/projects/:id/install` |

Удаление требует ввода имени проекта в подтверждении: каскад уносит туры, шаги и все
события (§8 [data-model.md](data-model.md)).

### S5. `/projects/:id/install` — установка виджета

| | |
|---|---|
| Запросы при входе | `GET /v1/projects/{id}`, `GET /v1/projects/{id}/snippet` |
| Отображает | готовый `<script>` с кнопкой копирования; `public_key`; список `allowed_origins`; статус «виджет подключён / не найден» из `widget_last_seen_at` |
| Блок для технических специалистов клиента | домены для `script-src`, вес бандлов, какие запросы уходит виджет, что хранится в localStorage (§3.4 idea.md) |
| Мутации | `PATCH /v1/projects/{id}` (`allowed_origins`) |
| Ключи Query | `['project', id]`, `['snippet', id]` |
| Состояния | пустой `allowed_origins` → явное предупреждение «виджет не будет работать» (fail closed, §8.1 vision.md) |

### S6. `/projects/:id/branding` — тема оформления

| | |
|---|---|
| Запросы при входе | `GET /v1/projects/{id}` |
| Отображает | поля `theme`: `primary_color`, `text_color`, `backdrop_opacity`, `border_radius`, `font_family`, подписи кнопок; живое превью подсказки |
| Мутации | `PATCH /v1/projects/{id}` (`theme`) |
| Ключи Query | `['project', id]` |
| Особенность | превью использует те же CSS-переменные, что виджет (§4.6 vision.md) |

## 5. Экраны туров

### S7. `/projects/:id/tours` — список туров

| | |
|---|---|
| Запросы при входе | `GET /v1/projects/{id}/tours` |
| Отображает | `name`, `status`, условие показа, **запуски и % завершения за 7 дней** |
| Мутации | `POST /v1/projects/{id}/tours`, `POST /v1/tours/{id}/publish`, `/unpublish`, `DELETE /v1/tours/{id}` |
| Ключи Query | `['tours', projectId]` |
| Состояния | пусто → приглашение создать первый тур |
| Переходы | тур → конструктор; «Аналитика» → экран воронки |

Метрики приходят **в том же ответе**, одним агрегатом на все туры проекта. Иначе
список из 20 туров дал бы 20 запросов аналитики (см. §6, пункт 2).

### S8. `/projects/:id/tours/:tid` — конструктор тура

| | |
|---|---|
| Запросы при входе | `GET /v1/tours/{id}` — тур **вместе со шагами**, одним запросом |
| Отображает | имя и статус тура; условие показа (`url_match_mode`, `url_match_value`), `show_once`; список шагов; форму выбранного шага (`selector`, `title`, `body`, `placement`); превью подсказки |
| Мутации | `PATCH /v1/tours/{id}` (имя, условие показа); `POST /v1/tours/{id}/steps`; `PATCH /v1/steps/{id}`; `DELETE /v1/steps/{id}`; `PUT /v1/tours/{id}/steps/order`; `POST /v1/tours/{id}/publish`; `POST /v1/tours/{id}/editor-session` |
| Ключи Query | `['tour', tourId]` |
| Состояния | нет шагов → кнопка «Опубликовать» выключена (публикация без шагов → 422) |
| Особенности | reorder оптимистичный, с откатом кэша по ошибке; на `window.focus` тур перезапрашивается — так подхватываются шаги, добавленные в режиме редактора |

Две кнопки выхода на сайт клиента, обе через `editor-session`. Адрес страницы
владелец вводит рядом с кнопкой: в проекте хранятся разрешённые домены, а не
страницы. Поле подставляет первый домен из `allowed_origins`; пока список пуст,
вместо формы стоит подсказка со ссылкой на экран «Установка». Вкладка
открывается по нажатию, до ответа сервера, иначе браузер блокирует её как
всплывающее окно без действия пользователя.

| Кнопка | Запрос | Что делает |
|---|---|---|
| «Выбрать на сайте» | `POST /v1/tours/{id}/editor-session` с `mode: "edit"` и адресом страницы | открывает сайт в режиме выбора элементов |
| «Превью» | тот же эндпоинт с `mode: "preview"` | проходит тур целиком, события аналитики не пишутся (T5.6) |

### S9. `/projects/:id/tours/:tid/analytics` — воронка

| | |
|---|---|
| Запросы при входе | `GET /v1/tours/{id}/analytics?range=7d` |
| Отображает | тоталы (запуски, завершили, пропустили, бросили); воронку по шагам с drop-off и подсветкой худшего шага; блок «Проблемы» (`step_target_missing`, `widget_error` с кодами) |
| Мутации | нет, экран только читает |
| Ключи Query | `['analytics', tourId, range]` |
| Состояния | нет событий → «тур ещё не запускали», с подсказкой проверить публикацию и условие показа |
| Особенность | переключатель периода — `7d` / `30d`, скользящие окна в UTC (§7.2 vision.md) |

### S10. `*` — 404 и нет доступа

Чужой или несуществующий `project_id` / `tour_id` даёт 404 от API
([ADR-0006](adr/0006-tenant-isolation-404.md)) — экран показывает «не найдено» без
различения «нет такого» и «не ваше».

## 6. Результаты сверки экранов и API

Сверка макетов §4.3 vision.md со списком эндпоинтов §8.2 нашла пять расхождений.
Все пять исправлены в контракте.

**1. Не было удаления проекта.** В модели данных каскад от `projects` описан, в панели
подтверждение с вводом имени предусмотрено, а эндпоинта не существовало.
Добавлен `DELETE /v1/projects/{id}`.

**2. Список туров нечем было наполнить.** Макет обещает «запуски и % завершения» в
строке тура, но единственным источником метрик был `GET /tours/{id}/analytics` — то
есть запрос на каждый тур. `GET /v1/projects/{id}/tours` теперь возвращает лёгкие
агрегаты за 7 дней (`runs_7d`, `completion_rate_7d`) одним `GROUP BY tour_id`.

**3. Конструктор требовал двух запросов.** `GET /v1/tours/{id}` теперь отдаёт тур
вместе со шагами: экран всё равно бесполезен без шагов, а два запроса дают мигание
интерфейса и две точки отказа.

**4. У превью не было способа отличить себя от настройки.** `POST
/v1/tours/{id}/editor-session` получил параметр `mode: "edit" | "preview"`. Без него
прогоны владельца писались бы в аналитику и портили его же воронку.

**5. Аналитика принимала `from`/`to`.** После решения о скользящих окнах (§7.2) это
противоречие: произвольный период требует календарных границ и таймзоны, которых в MVP
нет. Контракт — `?range=7d|30d`.

## 8. Какие данные где показываются

| Сущность | Поля на экранах | Где |
|---|---|---|
| `users` | `email` | шапка S1 |
| `projects` | `name`, `public_key`, `allowed_origins`, `widget_last_seen_at` | S4, S5 |
| `projects.theme` | цвета, радиус, прозрачность, шрифт, подписи кнопок | S6, превью в S8 |
| `tours` | `name`, `status`, `url_match_*`, `show_once`, `published_at` | S7, S8 |
| `steps` | `position`, `selector`, `title`, `body`, `placement` | S8 |
| `events` | только агрегаты: тоталы, воронка, drop-off, коды проблем | S7 (кратко), S9 |

Сырые события на экранах не показываются нигде — ни таблицы, ни выгрузки. Владельцу
нужны выводы, а не журнал; экспорт CSV — за границами MVP (§1.1 idea.md).

## 9. Чего на экранах нет

Правило: **нет эндпоинта — нет кнопки.** Отсутствуют сознательно, каждое со ссылкой
на решение:

- сброс и смена пароля, подтверждение email (§1.1 idea.md);
- приглашение коллег, роли, аудит-лог (§1.1);
- сегментация, расписание показов, A/B-версии тура (§2.4 idea.md);
- таблица и экспорт сырых событий (§8 выше);
- верификация домена проекта (§15 vision.md);
- биллинг и тарифы (§1.1).
