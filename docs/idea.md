# OnBoard — идея продукта

Версия: 1.1 · Дата: 2026-10-12 · Статус: согласовано

Первый документ проекта: что мы делаем, для кого и зачем. Технические решения —
в [vision.md](vision.md), план работ — в [tasklist.md](tasklist.md).

## 1. Контекст и цель

**Проблема.** При запуске продукта или редизайне пользователи не разбираются в новом
интерфейсе и уходят. Видео и FAQ отвлекают от приложения, а правка инструкций требует
релиза и участия разработчиков.

**Цель.** Дать владельцу веб-сервиса инструмент, которым он **сам, без разработчиков**,
собирает пошаговые подсказки поверх своего интерфейса и видит, доходят ли пользователи
до конца.

**Ценностное предложение в одном предложении.** Вставил один `<script>` один раз — дальше
меняешь обучение из личного кабинета без релизов.

### 1.1 Что входит в систему и что нет

| В границах MVP | Вне границ MVP |
|---|---|
| Встраиваемый JS-виджет для чужих сайтов | Мобильные SDK (iOS/Android, React Native) |
| Личный кабинет: авторизация, проекты, туры | Биллинг, тарифы, платежи |
| Конструктор шагов + визуальный выбор элемента | Командная работа, роли, аудит-лог |
| Аналитика: запуски, скипы, завершения, воронка | BI-конструктор отчётов, когорты, retention |
| Кастомизация цветов бренда | Полный визуальный редактор CSS подсказок |
| Один тип подсказки: tooltip + подсветка | Чеклисты, hotspot'ы, баннеры, NPS-опросы |
| Вход по email и паролю | Сброс пароля и подтверждение email (требуют SMTP) |
| Список разрешённых доменов проекта | Верификация владения доменом |

### 1.2 Рабочие допущения

Фиксирую явно — если допущение неверно, меняется объём работ:

1. Сайты клиентов — обычные веб-страницы (SSR или SPA) с доступом к DOM. Контент
   внутри сторонних `<iframe>` и внутри closed Shadow DOM виджет не достаёт.
2. Клиент может вставить один тег `<script>` в свой сайт. Это единственное, что
   требуется от его разработчиков, и только один раз.
3. Клиент готов открыть свой сайт в браузере для настройки тура (editor-mode).
   Прод-сайт или стейдж — на его выбор.
4. Масштаб MVP: десятки проектов, единицы миллионов событий в месяц. PostgreSQL
   достаточно, отдельное аналитическое хранилище не нужно.
5. Персональные данные конечных пользователей не собираем: ни email, ни имён, ни IP
   в сыром виде. Только анонимный `visitor_id` в localStorage.

## 2. Цели и задачи владельца сайта

Владелец сайта покупает не «виджет с подсказками». Он покупает решение конкретных
проблем, и если продукт их не решает, наличие подсказок его не интересует. Этот раздел
фиксирует, что именно считается решённым — чтобы на приёмке и в спорах о приоритетах
было к чему апеллировать.

Терминология: «владелец сайта» и «заказчик» в документах проекта — одно и то же лицо,
клиент платформы. Приёмка самого проекта — отдельная тема, §5.

### 2.1 Цели (зачем он нас внедряет)

| Цель | Что болит сейчас | Что работает на цель | По какому числу он поймёт |
|---|---|---|---|
| Удержать новых пользователей на первых сессиях | человек не разобрался в интерфейсе и ушёл молча, причину никто не узнал | тур на ключевом сценарии, запускается сам при первом визите | доля дошедших до финала тура; его собственная конверсия первого экрана |
| Снять с поддержки поток «где эта кнопка» | один и тот же вопрос приходит сотни раз, отвечают люди | подсказка возникает там, где вопрос, в момент вопроса | число тикетов категории «как сделать X» до и после |
| Довести новую функцию до использования | фичу выпустили, её не замечают; после редизайна ломается привычная траектория | тур по изменившимся элементам, только для тех, кто их ещё не видел | его метрика использования функции; наша — завершаемость тура |
| Перестать ждать релиз ради правки текста | «поправьте формулировку» уезжает в бэклог разработки на две недели | правка и публикация из панели, без участия разработчиков | срок от «заметили проблему в обучении» до «исправлено у пользователей» |
| Понимать, работает ли обучение | непонятно, помогает ли тур; решения принимаются на ощущениях | воронка по шагам, скипы, завершения | completion rate, skip rate, номер шага с худшим drop-off |

### 2.2 Задачи, в формулировке самого заказчика

| № | Задача |
|---|---|
| J1 | Когда я решил попробовать платформу, я хочу подключить её одним тегом и больше не возвращаться к разработчикам — чтобы внедрение не стояло в очереди релизов. |
| J2 | Когда мне нужно обучение, я хочу собрать его сам, не зная CSS и DOM — чтобы не зависеть от того, кто знает. |
| J3 | Когда я показываю на кнопку, я хочу, чтобы подсказка держалась за неё и после редизайна — чтобы обучение не рассыпалось от правки вёрстки. |
| J4 | Когда тур готов, я хочу показать его только на нужной странице и только один раз на человека — чтобы не раздражать тех, кто уже всё понял. |
| J5 | Когда я закончил сборку, я хочу посмотреть тур своими глазами на своём сайте — чтобы не публиковать вслепую. |
| J6 | Когда я заметил плохую формулировку, я хочу исправить её сегодня — чтобы не ждать релизного цикла. |
| J7 | Когда тур поработал неделю, я хочу знать, сколько людей дошли до конца и на каком шаге отваливаются — чтобы править то, что действительно сломано. |
| J8 | Когда тур перестал работать из-за правки вёрстки, я хочу узнать об этом от системы — чтобы не узнавать от пользователей. |
| J9 | Когда подсказка появляется в моём интерфейсе, я хочу, чтобы она выглядела моей — чтобы не казалась чужим баннером. |
| J10 | Когда я ставлю чужой скрипт на свой сайт, я хочу быть уверен, что он не замедлит и не сломает его и не соберёт лишних данных о моих пользователях — чтобы это прошло проверку безопасности. |

### 2.3 Чем каждая задача закрывается

| Задача | Возможность продукта | Задачи плана | Признак, что решена |
|---|---|---|---|
| J1 | один тег `<script>`, статус подключения в панели | T1.6, T2.1, T3.3 | на чистом сайте тур работает после вставки одного тега; панель показывает «подключён» |
| J2 | визуальный выбор элемента на своём сайте + конструктор шагов | T3.5, T5.1–T5.5 | тур из 4 шагов собран без ввода селектора руками |
| J3 | приоритет стабильных атрибутов при генерации селектора, `selector_candidates` | T5.3 | селектор предпочитает `data-*`/`id`, хэш-классы CSS-модулей отфильтрованы |
| J4 | `url_match`, `show_once`, прогресс в localStorage | T1.4, T2.5 | тур не показывается повторно и не появляется на посторонних страницах |
| J5 | предпросмотр тура на своём сайте | **T5.6 (новая)** | владелец проходит тур на своём сайте до публикации, аналитика при этом не пишется |
| J6 | публикация из панели, обновление конфига виджета | T1.4, T2.1 | правка текста видна на сайте без участия разработчиков |
| J7 | воронка по шагам, скипы, завершения | T4.1–T4.4 | числа в панели совпадают с прогоном 10 сессий, худший шаг подсвечен |
| J8 | событие `step_target_missing` и блок «Проблемы» | T2.2, T4.4 | после ломающей правки вёрстки панель показывает, какой шаг и какой селектор |
| J9 | тема проекта: цвета, радиус, подписи кнопок | T6.1, T6.2 | смена `primary_color` меняет вид подсказки без переустановки тега |
| J10 | бюджет размера, Shadow DOM, `try/catch`, отсутствие PII и cookie | инварианты №1–№8, T0.7, T2.8 | `make size` зелёный; виджет не ломает стенд с враждебным CSS; в БД нет IP и email конечных пользователей |

### 2.4 Чего продукт для заказчика не делает

Ожидания дешевле обсудить до разработки:

- **не заменяет документацию и справку.** Тур объясняет интерфейс в момент работы
  с ним, а не отвечает на вопросы про предметную область;
- **не исправляет плохой интерфейс.** Если кнопку невозможно найти, подсказка —
  обезболивающее, а не лечение. Иногда правильный вывод из нашей воронки — «переделайте
  экран», а не «перепишите подсказку»;
- **не работает в мобильных приложениях** и внутри сторонних `<iframe>`;
- **не сегментирует конечных пользователей** в MVP: нельзя показать тур только
  «новичкам из Москвы на тарифе Pro» — доступны URL страницы и «один раз на человека»;
- **не делает A/B-тесты** формулировок в MVP;
- **не знает, кто конкретно проходил тур.** Это ограничение по дизайну (§1.2): мы не
  собираем PII. Для заказчика это чаще плюс — внедрение проходит проверку
  безопасности, — но персональных разборов «как учился клиент Иванов» не будет.

### 2.5 Приоритет

| Приоритет | Задачи | Обоснование |
|---|---|---|
| Обязательно для MVP | J1, J2, J3, J4, J6, J7, J9, J10 | без любой из них продукт не решает заявленную цель и не проходит критерии §5 |
| Желательно в MVP | J5, J8 | резко повышают доверие к инструменту, но приёмка не падает без них |
| После MVP | сегментация, A/B, расписание показов, мультиязычность, чеклисты | §1.1, «вне границ» |

## 3. Акторы и заинтересованные лица

### 3.1 Акторы системы

Те, кто непосредственно работает с системой — для них проектируются интерфейсы:

| Актор | Кто это | Где работает | Главная задача |
|---|---|---|---|
| **Владелец сайта** (клиент платформы) | продакт, маркетолог, support-lead | личный кабинет | собрать тур, посмотреть воронку |
| **Конечный пользователь** | посетитель сайта клиента | сайт клиента | понять интерфейс и не бросить его |
| **Разработчик клиента** | фронтендер клиента | сайт клиента | один раз вставить сниппет |
| **Админ платформы** | мы | БД / CLI | диагностика, лимиты |

Роль админа в MVP не имеет UI — только доступ к БД и логам.

### 3.2 Заинтересованные лица

Круг шире акторов: часть этих людей никогда не откроет наш интерфейс, но может
остановить внедрение или обесценить продукт. Колонка «рычаг» — самая важная: влияние
без указания механизма ничего не значит.

| Заинтересованное лицо | Связь | Интерес | Рычаг влияния |
|---|---|---|---|
| **Владелец сайта** (продакт) | прямая | меньше оттока, меньше тикетов, не ждать релиза | решает о внедрении и об отказе; платит |
| **Конечный пользователь** | прямая | быстро понять интерфейс и не отвлекаться | формально никакого. Фактически — кнопка «Пропустить»: массовый скип обесценивает инструмент в глазах владельца |
| **Разработчик (фронтендер) клиента** | прямая | минимум работы, никакого влияния на производительность и вёрстку своего сайта | может просто не вставить сниппет или потребовать «сначала покажите, что это не сломает прод» |
| **Служба безопасности клиента** | косвенная | никакого исполнения чужого кода без понимания, что он делает | вето на сторонний скрипт; требования к CSP и к списку доменов |
| **Юрист / DPO клиента** | косвенная | не нарушить 152-ФЗ и GDPR при обработке данных посетителей | вето, если продукт собирает персональные данные или ставит cookie без согласия |
| **Поддержка клиента** | косвенная | не отвечать сто раз на один вопрос | союзник: приносит владельцу список реальных вопросов, то есть готовый сценарий тура |
| **Дизайн и бренд клиента** | косвенная | подсказки не выглядят чужеродным баннером | может потребовать отключить виджет из-за внешнего вида |
| **Разработчики браузеров** | косвенная | свои приоритеты приватности и производительности | меняют правила для сторонних скриптов и для хранилищ: Safari ограничивает время жизни script-writable storage, от этого зависит наш `show_once` |
| **Блокировщики рекламы и их фильтр-листы** | косвенная | блокировать трекеры | попадание нашего домена или пути в фильтр-лист выключает виджет у части посетителей |
| **Мы как владельцы платформы** | прямая | работающий продукт, который не создаёт инцидентов у клиентов | решения об архитектуре и приоритетах |
| **Заказчик проекта** (приёмка) | косвенная | проект соответствует критериям §5 | приёмка работы |
| **Будущий разработчик проекта** | косвенная | разобраться в коде и не бояться его менять | скорость доработок после сдачи |

### 3.3 Матрица влияние / интерес

```
                            ВЫСОКОЕ ВЛИЯНИЕ
   удовлетворять            │              управлять плотно
   (их интерес низкий,      │          (главные роли проекта)
    но вето — реальное)     │
                            │
 • Разработчик клиента      │   • Владелец сайта (продакт)
 • Служба безопасности      │   • Заказчик проекта
 • Юрист / DPO              │   • Мы как владельцы платформы
 • Браузеры                 │
 • Блокировщики             │
 ───────────────────────────┼───────────────────────────────── ИНТЕРЕС →
                            │
 • Конкуренты               │   • Конечный пользователь
 • Будущий разработчик      │   • Поддержка клиента
   (до сдачи проекта)       │   • Дизайн и бренд клиента
                            │
   наблюдать                │              держать в курсе
                            НИЗКОЕ ВЛИЯНИЕ
```

Две асимметрии, которые и делают этот анализ полезным:

- **конечный пользователь — максимальный интерес при почти нулевом влиянии.** Он не
  выбирал наш продукт, не может его настроить и не может пожаловаться нам. Поэтому
  его интересы приходится защищать архитектурно, а не по запросу;
- **разработчик и безопасник клиента — наоборот: низкий интерес при праве вето.** Им
  от нашего продукта нет никакой выгоды, зато есть риск получить инцидент на проде.
  Это самые недооценённые стейкхолдеры в таких продуктах.

### 3.4 Что из этого следует для продукта

Каждое следствие — конкретное, иначе анализ бесполезен:

| Стейкхолдер | Следствие | Где зафиксировано |
|---|---|---|
| Конечный пользователь | кнопка «Пропустить» видна всегда и не прячется; скип считается отдельной метрикой — это единственный канал его голоса, и он должен быть слышен владельцу | §4.4 vision.md, §7.2 vision.md |
| Конечный пользователь | не собираем о нём персональных данных, хотя технически могли бы: он не давал нам согласия и не может его отозвать | инвариант №7 |
| Разработчик клиента | его работа — ровно один тег, никаких `identify`, никаких вторых скриптов для метрик | T1.6, §6 competitors.md |
| Разработчик клиента | виджет не имеет права сломать его сайт: `try/catch`, Shadow DOM, никаких правок чужого DOM | инварианты №1–№3 |
| Служба безопасности | на экране установки — ответы на её вопросы: какие домены добавить в `script-src`, сколько весит, какие запросы уходят, что хранится в localStorage | T3.3 |
| Юрист / DPO | на сайте клиента не ставится ни одна cookie, в БД нет IP и сырого User-Agent; это снимает тему согласия на обработку персональных данных | инвариант №7, §1.2 |
| Поддержка клиента | ничего не строим специально, но воронка и блок «Проблемы» — это то, что владелец покажет поддержке; их вопросы становятся шагами тура | T4.4 |
| Дизайн и бренд | тема проекта: цвета, радиус, подписи кнопок; превью совпадает с реальным видом | T6.1, T6.2 |
| Браузеры | ограничения хранилищ проверяем руками в Safari и iOS, отдельным пунктом приёмки; при недоступном localStorage тур деградирует, а не падает | A8, §4.3 |
| Блокировщики | нейтральные имена путей и файлов, без `track`, `analytics`, `ads` в URL | §10 vision.md |
| Заказчик проекта | критерии §5 разобраны в таблицу трассировки и в чеклист приёмки A1–A9 | §13 vision.md, tasklist.md |
| Будущий разработчик | onboarding-документ, по которому проект поднимается без обращения к другим файлам | T6.3 |

## 4. Пользовательские сценарии

### 4.1 Основной сценарий владельца (happy path)

```
Регистрация → создаётся проект → копирует сниппет → вставляет на сайт
   → панель показывает «виджет подключён ✓» (пришёл первый пинг)
   → создаёт тур «Знакомство с новым дашбордом»
   → жмёт «Выбрать элементы на сайте» → открывается его сайт в режиме выбора
   → клик по кнопке «Фильтры» → вводит текст подсказки → «Добавить шаг»
   → ещё 3 шага → закрывает вкладку → возвращается в панель
   → проверяет порядок шагов, настраивает цвет бренда → «Опубликовать»
   → через день открывает «Аналитика»: 240 запусков, 38% скипов, 54% дошли до конца
   → видит провал на шаге 3, переписывает текст, публикует заново
```

Критическая метрика продукта — **time to first published tour**. Целевое значение
для MVP: ≤ 10 минут от регистрации. Это главный ориентир при проектировании UX панели.

### 4.2 Сценарий конечного пользователя

```
Открывает сайт → загружается loader (async, ~4 КБ) → loader спрашивает конфиг
   → есть опубликованный тур, подходящий под URL, и этот visitor его не проходил
   → подгружается ядро виджета → ждёт появления элемента первого шага
   → затемнение фона, «окно» вокруг кнопки «Фильтры», рядом tooltip
      «Здесь теперь фильтры. Нажмите, чтобы сузить выборку» [Пропустить] [Далее 1/4]
   → Далее → Далее → Далее → «Готово»
   → виджет убирает оверлей, помечает тур пройденным, больше не показывает
```

### 4.3 Негативные и краевые сценарии

Эти ветки важнее happy path — на них ломаются подобные виджеты:

| Сценарий | Ожидаемое поведение |
|---|---|
| Элемент шага не найден | ждём до 10 с (MutationObserver), затем событие `step_target_missing`, тур корректно закрывается, пользователь не видит пустой подсказки |
| Элемент за пределами экрана | плавный `scrollIntoView`, затем позиционирование |
| Элемент перекрыт модалкой клиента | позиционирование пересчитывается, оверлей всегда ниже tooltip по z-index |
| Пользователь перешёл на другую страницу посреди тура | прогресс сохранён в localStorage; на подходящем URL тур продолжается с того же шага |
| SPA сменила роут без перезагрузки | перехват `pushState`/`replaceState`/`popstate` → перепроверка URL-условий |
| CSP сайта блокирует наш домен | виджет не загружается; в панели — диагностика «проверьте script-src» |
| Два тура подходят под URL | показываем один — с наивысшим приоритетом (в MVP: самый свежий опубликованный) |
| API аналитики недоступен | события буферизуются в памяти и localStorage, отправка повторяется; тур работает |
| Мобильный экран < 480px | tooltip растягивается на всю ширину снизу, подсветка сохраняется |
| Отключён localStorage | виджет работает, но тур может показаться повторно (деградация, не поломка) |

## 5. Критерии оценки проекта

Формулировки из технического задания — то, по чему проект будет приниматься:

1. Разработан независимый легковесный JS-скрипт, который корректно встраивается на
   сторонние веб-ресурсы и взаимодействует с их DOM-деревом (подсветка нужных
   элементов, вывод всплывающих окон поверх интерфейса).
2. Реализована веб-панель управления для владельцев сайтов (клиентов платформы).
3. В панели работает конструктор сценариев: цепочка шагов, привязка шага к CSS-селектору,
   текст подсказки.
4. Реализована система сбора базовой аналитики: количество запусков онбординга, число
   пропусков (скипов), процент пользователей, дошедших до финального шага.
5. Предусмотрена базовая визуальная кастомизация подсказок (корпоративные цвета)
   через личный кабинет.

Как каждый критерий закрывается технически — [vision.md §13](vision.md).
Как проверяется — раздел «Приёмка проекта» в [tasklist.md](tasklist.md).
