## 1. Контекст и цель

**Проблема.** При запуске продукта или редизайне пользователи не разбираются в новом
интерфейсе и уходят. Видео и FAQ отвлекают от приложения, а правка инструкций требует
релиза и участия разработчиков.

**Цель.** Дать владельцу веб-сервиса инструмент, которым он **сам, без разработчиков**,
собирает пошаговые подсказки поверх своего интерфейса и видит, доходят ли пользователи
до конца.

**Ценностное предложение в одном предложении.** Вставил один `<script>` один раз — дальше
меняешь обучение из личного кабинета без релизов.

### 1.1 Что входит в систему и что нет

| В границах MVP | Вне границ MVP |
|---|---|
| Встраиваемый JS-виджет для чужих сайтов | Мобильные SDK (iOS/Android, React Native) |
| Личный кабинет: авторизация, проекты, туры | Биллинг, тарифы, платежи |
| Конструктор шагов + визуальный выбор элемента | Командная работа, роли, аудит-лог |
| Аналитика: запуски, скипы, завершения, воронка | BI-конструктор отчётов, когорты, retention |
| Кастомизация цветов бренда | Полный визуальный редактор CSS подсказок |
| Один тип подсказки: tooltip + подсветка | Чеклисты, hotspot'ы, баннеры, NPS-опросы |

### 1.2 Рабочие допущения

Фиксирую явно — если допущение неверно, меняется объём работ:

1. Сайты клиентов — обычные веб-страницы (SSR или SPA) с доступом к DOM. Контент
   внутри сторонних `<iframe>` и внутри closed Shadow DOM виджет не достаёт.
2. Клиент может вставить один тег `<script>` в свой сайт. Это единственное, что
   требуется от его разработчиков, и только один раз.
3. Клиент готов открыть свой сайт в браузере для настройки тура (editor-mode).
   Прод-сайт или стейдж — на его выбор.
4. Масштаб MVP: десятки проектов, единицы миллионов событий в месяц. PostgreSQL
   достаточно, отдельное аналитическое хранилище не нужно.
5. Персональные данные конечных пользователей не собираем: ни email, ни имён, ни IP
   в сыром виде. Только анонимный `visitor_id` в localStorage.

## 2. Акторы

| Актор | Кто это | Где работает | Главная задача |
|---|---|---|---|
| **Владелец сайта** (клиент платформы) | продакт, маркетолог, support-lead | личный кабинет | собрать тур, посмотреть воронку |
| **Конечный пользователь** | посетитель сайта клиента | сайт клиента | понять интерфейс и не бросить его |
| **Разработчик клиента** | фронтендер клиента | сайт клиента | один раз вставить сниппет |
| **Админ платформы** | мы | БД / CLI | диагностика, лимиты |

Роль админа в MVP не имеет UI — только доступ к БД и логам.

## 3. Пользовательские сценарии

### 3.1 Основной сценарий владельца (happy path)

```
Регистрация → создаётся проект → копирует сниппет → вставляет на сайт
   → панель показывает «виджет подключён ✓» (пришёл первый пинг)
   → создаёт тур «Знакомство с новым дашбордом»
   → жмёт «Выбрать элементы на сайте» → открывается его сайт в режиме выбора
   → клик по кнопке «Фильтры» → вводит текст подсказки → «Добавить шаг»
   → ещё 3 шага → закрывает вкладку → возвращается в панель
   → проверяет порядок шагов, настраивает цвет бренда → «Опубликовать»
   → через день открывает «Аналитика»: 240 запусков, 38% скипов, 54% дошли до конца
   → видит провал на шаге 3, переписывает текст, публикует заново
```

Критическая метрика продукта — **time to first published tour**. Целевое значение
для MVP: ≤ 10 минут от регистрации. Это главный ориентир при проектировании UX панели.

### 3.2 Сценарий конечного пользователя

```
Открывает сайт → загружается loader (async, ~4 КБ) → loader спрашивает конфиг
   → есть опубликованный тур, подходящий под URL, и этот visitor его не проходил
   → подгружается ядро виджета → ждёт появления элемента первого шага
   → затемнение фона, «окно» вокруг кнопки «Фильтры», рядом tooltip
      «Здесь теперь фильтры. Нажмите, чтобы сузить выборку» [Пропустить] [Далее 1/4]
   → Далее → Далее → Далее → «Готово»
   → виджет убирает оверлей, помечает тур пройденным, больше не показывает
```

### 3.3 Негативные и краевые сценарии

Эти ветки важнее happy path — на них ломаются подобные виджеты:

| Сценарий | Ожидаемое поведение |
|---|---|
| Элемент шага не найден | ждём до 10 с (MutationObserver), затем событие `step_target_missing`, тур корректно закрывается, пользователь не видит пустой подсказки |
| Элемент за пределами экрана | плавный `scrollIntoView`, затем позиционирование |
| Элемент перекрыт модалкой клиента | позиционирование пересчитывается, оверлей всегда ниже tooltip по z-index |
| Пользователь перешёл на другую страницу посреди тура | прогресс сохранён в localStorage; на подходящем URL тур продолжается с того же шага |
| SPA сменила роут без перезагрузки | перехват `pushState`/`replaceState`/`popstate` → перепроверка URL-условий |
| CSP сайта блокирует наш домен | виджет не загружается; в панели — диагностика «проверьте script-src» |
| Два тура подходят под URL | показываем один — с наивысшим приоритетом (в MVP: самый свежий опубликованный) |
| API аналитики недоступен | события буферизуются в памяти и localStorage, отправка повторяется; тур работает |
| Мобильный экран < 480px | tooltip растягивается на всю ширину снизу, подсветка сохраняется |
| Отключён localStorage | виджет работает, но тур может показаться повторно (деградация, не поломка) |

## 4. Критерии оценки от заказчика

Формулировки из технического задания — то, по чему проект будет приниматься:

1. Разработан независимый легковесный JS-скрипт, который корректно встраивается на
   сторонние веб-ресурсы и взаимодействует с их DOM-деревом (подсветка нужных
   элементов, вывод всплывающих окон поверх интерфейса).
2. Реализована веб-панель управления для владельцев сайтов (клиентов платформы).
3. В панели работает конструктор сценариев: цепочка шагов, привязка шага к CSS-селектору,
   текст подсказки.
4. Реализована система сбора базовой аналитики: количество запусков онбординга, число
   пропусков (скипов), процент пользователей, дошедших до финального шага.
5. Предусмотрена базовая визуальная кастомизация подсказок (корпоративные цвета)
   через личный кабинет.

Как каждый критерий закрывается технически — [vision.md §13](vision.md).
Как проверяется — раздел «Приёмка проекта» в [tasklist.md](tasklist.md).
