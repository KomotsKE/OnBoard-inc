# Процесс разработки с AI

Версия: 1.1 · Обновлён: 2026-10-23

Документ описывает, как именно мы ведём разработку OnBoard в паре «вы + Claude».
Цель процесса одна: **чтобы качество кода не зависело от того, насколько удачно
сформулирован запрос**. Это достигается не доверием к модели, а проверяемыми целями
и зафиксированными инвариантами.

---

## 1. Главный принцип: задача = проверяемая цель

Расплывчатая задача («сделай аутентификацию») заставляет меня догадываться и
порождает код, который потом переписывается. Задача с критерием приёмки
(«регистрация, вход, refresh; тест: неверный пароль → 401, чужой project_id → 404»)
позволяет работать автономно и даёт однозначный ответ «готово / не готово».

Поэтому каждая задача в [tasklist.md](tasklist.md) имеет строку `проверка:` с
конкретной командой или сценарием. Задача без такой строки в работу не берётся —
сначала формулируем критерий.

Формат задачи:

```
### T2.4 Tooltip в Shadow DOM с позиционированием
Цель:      подсказка рядом с элементом, с flip/shift при нехватке места
Файлы:     widget/src/core/tooltip.ts, widget/tests/tooltip.test.ts
Проверка:  make test + e2e/tooltip.spec.ts — 4 позиции на стенде с враждебным CSS
Инварианты: №2 (Shadow DOM), №5 (бюджет размера)
Зависит:   T2.2
```

## 2. Жизненный цикл одной задачи

```
1. Уточнение   Я читаю задачу. Если формулировка допускает две трактовки —
               называю их и спрашиваю. Молча не выбираю.
2. План        Для задачи, затрагивающей >1 файла, сначала даю план в 3–6 строк:
               что меняю, где, как проверю. Вы подтверждаете или правите.
3. Тест        Где применимо — сначала тест, который падает по делу
               (не из-за опечатки, а из-за отсутствия функциональности).
4. Код         Минимальная реализация, закрывающая задачу. Без запаса «на будущее».
5. Проверка    Запускаю команды из строки «проверка». Падает — исправляю сам
               и перезапускаю, не перекладывая на вас.
6. Дифф        Показываю изменения и явно называю: что сделано, что осталось
               за рамками, какие допущения принял.
7. Закрытие    Вы принимаете → отмечаю задачу в бэклоге, по вашей просьбе коммичу.
```

Шаг 5 — ключевой. Я не сообщаю «готово», пока не выполнил проверку. Если проверку
выполнить невозможно (см. §3), я говорю об этом прямо и выдаю вам готовые команды
с ожидаемым результатом — но не выдаю непроверенное за проверенное.

## 3. Матрица проверок: кто что может

Проверено в этом окружении 2026-10-12: Python 3.12.3, Node 20.20, npm 10.8,
Docker 29.1 + Compose v5 (демон отвечает), git 2.43; pypi, npm registry и Docker Hub
доступны, `pip install` в venv работает.

| Проверка | Кто выполняет | Команда / примечание |
|---|---|---|
| Юнит/интеграционные тесты бэкенда | **я** | `make test` |
| Юнит-тесты виджета | **я** | `vitest` в составе `make test` |
| Типы и линт | **я** | `make lint` |
| Миграции вперёд/назад на чистой БД | **я** | `make migrate`, `alembic downgrade base` |
| Подъём всего стека | **я** | `make up`, затем `curl localhost:8000/health` |
| Запросы к API | **я** | `curl` / httpx в тестах |
| Бюджет размера бандлов | **я** | `make size` |
| E2E в Chromium (виджет на стенде, панель) | **я** | `make e2e`; первый запуск скачивает Chromium (~150 МБ, медленно) |
| Поведение в Firefox | **я** (с оговоркой) | Playwright firefox; расхождения с реальным браузером возможны |
| **Safari / iOS Safari** | **вы** | движка нет в окружении; критично для виджета — ручной чеклист перед сдачей |
| **Виджет на реальном сайте** (не на стенде) | **вы** | CSP, блокировщики, реальный CSS — только живая проверка |
| Доступность: клавиатура и axe-core | **я** | `make e2e`; проход без мыши и отсутствие критичных нарушений |
| **Чтение экранным диктором** (NVDA, VoiceOver) | **вы** | движка озвучки в окружении нет; axe проверяет разметку, а не то, как её читают |
| **Визуальная оценка UI** | **вы** | я проверяю наличие и работу элементов, не «красиво ли» |
| **CI в GitHub Actions** | **вы** | нужен remote; я пишу workflow, запускаете вы |
| **Деплой на сервер** | **вы** | вне окружения |

Правило: если проверка в столбце «вы» — я останавливаюсь на правке и даю команды
с описанием ожидаемого результата и типичных вариантов падения. Не пытаюсь
изобразить проверку, которую не могу выполнить.

## 4. Definition of Done

Задача закрыта, когда выполнено всё:

- [ ] критерий из строки «проверка» выполнен, команда запущена, вывод показан
- [ ] `make lint` и `make test` зелёные (не только новый тест, весь набор)
- [ ] ни один инвариант из CLAUDE.md не нарушен
- [ ] дифф содержит только то, что требует задача (нет попутных «улучшений»)
- [ ] не осталось «сирот»: импортов, переменных, функций, ставших неиспользуемыми
      из-за этих правок
- [ ] пройден чеклист §10 [conventions.md](conventions.md): чистый код, комментарии
      «почему», README компонента соответствует новому поведению
- [ ] явно сказано, что осталось за рамками и какие допущения приняты

## 5. Гранулярность задач

- Одна задача = одна проверяемая цель = один коммит.
- Ориентир объёма — до ~300 строк диффа. Больше — делим: крупный дифф невозможно
  осмысленно отревьюить, а значит ошибки проходят.
- Параллельно в работе ровно одна задача. Статус `→` в бэклоге стоит максимум
  у одной строки.
- Задача, которая «заодно» меняет три слоя (БД + API + UI), почти всегда делится
  на три.

## 6. Что тестируем обязательно, а что нет

Тесты — инструмент, а не ритуал. Покрываем то, что ломается молча и дорого.

**Обязательно:**
- изоляция арендаторов (матрица: 2 пользователя × 2 проекта × все приватные маршруты);
- формулы метрик §7.2 vision.md — на фикстуре событий с заранее посчитанными числами;
- идемпотентность ingest (двойная отправка батча → одна строка);
- `ElementResolver`: элемент есть / появляется позже / не появляется никогда;
- генератор селекторов: `data-testid`, сгенерированный id, хэш-классы CSS-модулей,
  `nth-of-type`, требование уникальности;
- безопасность: `<img onerror>` в тексте шага не исполняется; чужой/просроченный
  editor-токен отбивается;
- полный проход тура и скип на стенде (e2e).

**Не тестируем юнитами:**
- вёрстку и стили панели — только e2e на наличие и работу элементов;
- тривиальные CRUD-обёртки без логики;
- сторонние библиотеки.

## 7. Передача контекста между сессиями

Диалог не бесконечен, и новая сессия начинается без памяти о предыдущей. Поэтому
состояние проекта живёт в файлах, а не в переписке:

| Файл | Отвечает на вопрос |
|---|---|
| `docs/idea.md` | что и для кого мы делаем, цели и задачи заказчика, границы MVP |
| `docs/vision.md` | как устроена система; §15 — зафиксированные решения |
| `docs/adr/` | почему принято именно это решение и что отвергли |
| `CLAUDE.md` + `docs/conventions.md` | по каким правилам пишем код |
| `docs/tasklist.md` | где мы сейчас, что следующее, какие замечания накопились |

Правила:
- **задача берётся в работу отметкой `[→]` до начала кода**, а не после. В работе
  одновременно не больше одной; отметка снимается только переводом в `[x]`.
  Согласованность отметки, строки «Текущая задача» и счётчиков проверяет хук
  `scripts/check-tasklist.py` — декларативное правило без проверки рассыпается
  (так и вышло: `[→]` был описан в двух документах и ни разу не поставлен);
- закрывая задачу, ставлю `[x]`, обновляю блок «Прогресс» (счётчик, текущая задача,
  дата) и при необходимости добавляю строку в «Замечания»;
- шаги, которые вы выполняете руками (токены, переменные окружения, установка
  Chromium), оформляются инструкцией в `docs/guides/` — в той задаче, где впервые
  понадобились, а не задним числом;
- архитектурное решение, которое дорого менять, оформляется записью в `docs/adr/`
  (контекст, решение, альтернативы, последствия) — до реализации, а не после;
- продуктовое решение, принятое в диалоге, сразу вносится в `idea.md` или `vision.md`,
  а архитектурное — новой записью в `adr/`; иначе через две сессии его не существует.

### 7.1 Как возобновить работу

Последовательность для новой сессии — или для той же после обрыва. По шагам,
потому что «посмотри, где мы остановились» каждый раз выполняется по-разному:

1. **`git log --oneline -5` и `git status`.** Что сделано и нет ли незакоммиченных
   правок. Коммиты несут `Refs: TX.Y`, поэтому по истории видно, какие задачи закрыты.
2. **`docs/tasklist.md`:** блок «Прогресс», задача со статусом `[→]`, раздел
   «Замечания» — там лежит то, что замечено по пути и сознательно не починено.
3. **Грязное дерево — это незаконченная задача `[→]`, а не мусор.** Дочитать её
   критерий и довести, а не начинать заново: заново почти всегда означает потерять
   найденное в прошлый раз.
4. **`make up && make test`.** Убедиться, что отправная точка зелёная. Иначе первое
   падение спишут на свои правки и будут искать его не там.
5. **Перед кодом — `docs/conventions.md`,** особенно §9 (практики) и §12 (правила
   роста). Инварианты уже подгружены из `CLAUDE.md`.

Чего делать не нужно: перечитывать всю документацию целиком. 4000 строк в контекст
не нужны — `CLAUDE.md` даёт карту, остальное читается по ссылке, когда понадобится.

## 8. Как со мной эффективнее разговаривать

Не правила вежливости, а то, что измеримо влияет на результат:

| Вместо этого | Так |
|---|---|
| «сделай аналитику» | «эндпоинт `GET /tours/{id}/analytics` по формулам §7.2 vision.md; тест на фикстуре из 10 прогонов» |
| «почини, не работает» | текст ошибки / что ожидали / что получили |
| «давай сделаем всё 2-го этапа» | одна задача за раз, по порядку из бэклога |
| «сделай красиво» | укажите образец или конкретные правки: отступы, порядок блоков |
| «добавь на будущее настройку X» | добавляем, когда появится второе использование |

Полезные фразы: «покажи план перед кодом», «покажи дифф», «запусти проверку»,
«это слишком сложно — упрости», «оставь как было».

## 9. Роли

**Вы:** продуктовые решения, приоритет задач, приёмка по критериям, проверки из
столбца «вы» в §3.

**Я:** уточняющие вопросы до реализации, план, тесты, код, самостоятельная проверка,
честный отчёт о том, что не проверено. Внутри моей части работа разделена на семь
ролей-агентов — §12. Возражаю, когда вижу путь проще, и говорю прямо,
когда задача кажется переусложнённой.

## 10. Git

- Репозиторий инициализируется до первой задачи — без него нет ни диффов, ни откатов.
- **Пока нет remote и PR-ревью: один коммит на задачу прямо в `main`.** Ветка на
  задачу — лишний шаг, когда ревьюер и автор смотрят один рабочий каталог; откат
  делается `git revert` одного коммита. Ветки вводим в тот момент, когда появится
  remote и ревью через PR.
- Сообщение коммита — **Conventional Commits**, формат и перечень типов и скоупов в
  §11 [conventions.md](conventions.md). Коротко:
  `feat(backend): аутентификация по JWT`, тело с «почему» при необходимости, футер
  `Refs: T1.2`. Нарушение формата не даст сделать коммит — работает хук `commit-msg`.
- Хуки ставятся один раз: `make hooks`. Они же прогоняются в CI (`pre-commit run
  --all-files`), чтобы коммит в обход хуков не прошёл незамеченным.
- Откат вместо героизма: если задача ушла не туда, проще вернуться к последнему
  коммиту, чем «дочинивать» в три приёма.

## 11. Откуда модель берёт правила

Методика описана для Cursor, где `conventions.md` и `workflow.md` копируются в
`.cursor/rules/*.mdc` с режимом применения Always. В Claude Code тот же механизм
встроен: файл `CLAUDE.md` в корне проекта подгружается автоматически в каждую сессию.

Поэтому:

- `CLAUDE.md` — аналог Always-правил: индекс документов, порядок работы над задачей,
  стек, команды и десять инвариантов. Он сознательно короткий: чем длиннее файл
  постоянных правил, тем хуже он соблюдается;
- `docs/conventions.md` — подробный стиль кода, читается перед написанием кода;
- `docs/workflow.md` (этот файл) — процесс, читается при спорах о порядке работы.

Если вы будете параллельно работать в Cursor, те же два документа копируются
в `.cursor/rules/conventions.mdc` и `.cursor/rules/workflow.mdc` — копии создаются
по запросу, чтобы не завести второй расходящийся источник правды.

## 12. Конвейер агентов

Процесс из §2 выполняется не одной ролью, а семью: у каждой свой промпт, свой набор
прав и своя зона ответственности. Смысл разделения не в «команде», а в том, что
исполнитель не проверяет сам себя: критик смотрит план до кода, ревьюэр — дифф после,
и ни один из них не умеет править файлы.

Запуск: `/task T8.6` (или просто «берём T8.6»). Порядок и правила — в
`.claude/skills/task/SKILL.md`, определения ролей — в `.claude/agents/`.

| Роль | Файл | Права | Отвечает за |
|---|---|---|---|
| Аналитик | `analyst.md` | чтение | план 3–6 строк, критерий приёмки, файлы, инварианты, вопросы |
| Критик | `critic.md` | чтение | возражения к плану: KISS/YAGNI, пропущенные инварианты и ADR, путь проще |
| Тестировщик | `tester.md` | тесты и фикстуры | падающий тест по делу + запуск, показывающий падение |
| Бекендер | `backend-dev.md` | `backend/` | FastAPI, SQLAlchemy async, Alembic; инварианты №4, 7, 8, 9, 12 |
| Фронтендер панели | `panel-dev.md` | `panel/` | React, TanStack Query; инварианты №6, 10, 11 |
| Фронтендер виджета | `widget-dev.md` | `widget/`, `testsite/` | Shadow DOM, ноль зависимостей; инварианты №1, 2, 3, 5, 6 |
| Ревьюэр | `reviewer.md` | чтение + запуск проверок | DoD §4, чеклист §10 conventions, вердикт |

Виджет отделён от панели не по объёму, а по требованиям: его инварианты (гашение
ошибок, Shadow DOM, один глобал, бюджет размера) не действуют в панели, а правила
панели (TanStack Query, токены оформления, хранение сессии) не действуют в виджете.
Один промпт на оба набора разбавляет и то, и то.

### Цепочка

```
аналитик → критик → [КТ-1: вы подтверждаете план] → отметка [→] в tasklist
        → тестировщик → исполнитель(и) → ревьюэр → [КТ-2: вы принимаете дифф]
```

Для правки в одном файле без новой логики (текст, константа, опечатка) цепочка
короче: аналитик → КТ-1 → исполнитель → ревьюэр → КТ-2. Критик всё равно обязателен,
если задача добавляет зависимость, модуль или абстракцию либо касается инварианта.
Ревьюэр и обе контрольные точки не пропускаются никогда.

### Чего разделение не даёт

- **Не ускоряет.** Семь ролей дороже и медленнее одной: субагент не наследует
  контекст и перечитывает нужное сам. Выигрыш — в том, что план успевают оспорить
  до кода, а не после.
- **Не заменяет вашу приёмку.** Вердикт ревьюэра «принимать» — вход для КТ-2, а не
  её результат. Проверки из столбца «вы» в §3 остаются за вами в полном объёме.
- **Не отменяет проверки.** «Ревьюэр посмотрел» не равно «`make test` зелёный».
  Команда из строки `проверка:` запускается, её вывод показывается.
