# Соглашения по разработке

Версия: 1.0 · Дата: 2026-10-12

Как мы пишем код в этом проекте. Жёсткие инварианты, нарушение которых блокирует
задачу, — в [../CLAUDE.md](../CLAUDE.md); здесь они не дублируются. Что мы строим —
[vision.md](vision.md). Этот документ описывает стиль и структуру, а не архитектуру.
Принципы, которым подчиняются все правила ниже, — §9; чеклист перед сдачей задачи — §10.

## 1. Структура репозитория

```
backend/
  app/
    api/v1/public/      эндпоинты для виджета (без JWT, по public_key)
    api/v1/panel/       эндпоинты панели (JWT)
    core/               config.py, security.py, deps.py
    db/                 session.py, base.py
    models/             SQLAlchemy-модели, по одному файлу на агрегат
    schemas/            Pydantic-схемы запросов и ответов
    services/           бизнес-логика, не зависящая от FastAPI
  alembic/              миграции
  scripts/              инструменты разработчика (seed), в прод-образ не попадают
  tests/                тесты, зеркалят структуру app/
panel/
  src/api/              клиент API и типы ответов
  src/pages/            по одному файлу на экран из §4.3 vision.md
  src/components/       переиспользуемые куски UI
  src/hooks/            хуки TanStack Query
widget/
  src/loader/           точка входа loader.js
  src/core/             движок тура: engine, resolver, overlay, tooltip, analytics
  src/editor/           режим выбора элементов
  tests/                vitest
testsite/               стенд с враждебным CSS для проверки виджета
e2e/                    Playwright-сценарии
docs/                   idea, vision, adr, conventions, workflow, tasklist, guides
```

Новый каталог верхнего уровня — повод обсудить, а не создать молча.

Репозиторий один (монорепо), наружу `backend/`, `panel/` и `widget/` публикуются как
зеркала поддеревьев — [ADR-0007](adr/0007-monorepo-with-subtree-publishing.md). Поэтому:

- коммит по задаче может затрагивать несколько компонентов — это нормально и желательно;
- код не шарится между компонентами через относительные импорты вверх
  (`../../backend/...`): после публикации поддерева такой импорт окажется битым.
  Общее — только через HTTP-контракт;
- адреса внешних репозиториев живут в `.env`, а не в `Makefile`.

## 2. Python

- ruff как линтер и форматтер, длина строки 100.
- Типы на всех публичных функциях. `Any` — только с комментарием, почему иначе нельзя.
- SQLAlchemy 2.0 в асинхронном режиме: `AsyncSession`, `Mapped[...]` /
  `mapped_column(...)`, без legacy-`Column`. Связи — только явной загрузкой
  (`selectinload`), ленивой в async нет ([ADR-0010](adr/0010-async-backend.md)).
- Обработчики и сервисы — `async def`. Правила, которые из этого следуют (блокирующие
  вызовы, пулы, таймауты), — §12.
- Слои: обработчик FastAPI парсит вход и вызывает `services/`; бизнес-логика в
  обработчиках не живёт. Исключение — тривиальный CRUD без логики, он может быть
  в обработчике целиком.
- Имена схем: `ProjectCreate`, `ProjectUpdate`, `ProjectRead`. Модель и схема никогда
  не называются одинаково.
- Зависимости FastAPI — в `core/deps.py`, по одной на сущность
  (`get_current_user`, `get_owned_project`, `get_owned_tour`).
- Исключения: `HTTPException` поднимаем только в слое API; сервисы поднимают
  собственные типы или возвращают результат.
- Настройки — только через `core/config.py` (pydantic-settings). `os.getenv` в коде
  приложения не используется.

## 3. Миграции

- Только Alembic, только через `make revision m="…"`.
- `alembic check` обязан быть чистым: модели и схема описывают одну и ту же базу.
  Индексы в моделях объявляются с теми же именами, что в миграции, — иначе проверка
  видит расхождение там, где его нет.
- Каждая миграция обязана откатываться: `downgrade` пишется и проверяется, а не
  оставляется с `pass`.
- Миграция входит в ту же задачу, что и модель, которую она обслуживает.

## 4. API

- Версия в пути: `/v1/...`. Публичные маршруты — под `/v1/public/`, остальные
  требуют JWT.
- Коды: 200/201 — успех, 204 — ingest событий, 401 — нет или просрочен токен,
  403 — запрещённый Origin, 404 — объект не найден **или** не принадлежит
  пользователю, 409 — конфликт уникальности, 422 — ошибка валидации.
- Тело ошибки — по [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) (`Problem
  Details`), media type `application/problem+json`:
  `{"type": "/errors/tour-not-found", "title": "Тур не найден", "status": 404,
  "detail": "..."}`. Машиночитаемый идентификатор — `type`, и только он; по `detail`
  никакая логика не ветвится, это текст для человека. Свой формат ошибок не изобретаем.
- Ответы — всегда Pydantic-схемы, никогда `dict` «как получилось».
- Публичный API виджета не ломает обратную совместимость: на чужих сайтах живут
  старые версии скрипта. Поля только добавляются.

## 5. React (панель)

- Функциональные компоненты, хуки. Классовых компонентов нет.
- Серверное состояние — только TanStack Query; локальное — `useState`.
  Redux, MobX, Zustand и прочие сторы не добавляем.
- Access-токен — только в памяти провайдера, никогда в `localStorage`
  ([ADR-0008](adr/0008-session-storage.md)). В `localStorage` панели не хранится
  ничего, кроме UI-мелочей (последний выбранный проект, свёрнутые блоки).
- Обработка 401 и refresh живут в одном месте — `src/api/client.ts`. В хуках и
  компонентах проверок «а не истёк ли токен» нет.
- Запросы к API — только через `src/api/` и хуки в `src/hooks/`; `fetch` внутри
  компонента запрещён.
- Ключи запросов — по соглашению из §4.6 vision.md, от общего к частному; инвалидация
  по префиксу, а не `invalidateQueries()` без аргументов.
- У каждого экрана обработаны три состояния: загрузка, ошибка, пусто. Белый экран
  при ошибке запроса — дефект.
- Один экран = один файл в `src/pages/`. Компонент длиннее ~200 строк делится.
- Стили — CSS-модули, без UI-библиотек (цель — не тащить дизайн-систему в MVP).
- Строки — по-русски прямо в разметке, без i18n-словарей.

## 6. Виджет

- ES2020, без полифилов и транспиляции в ES5.
- Ноль рантайм-зависимостей. Любая внешняя библиотека в виджете — отдельное
  обсуждение с замером влияния на бюджет размера.
- Модули — фабрики, возвращающие объект с методами (`createTooltip(...)`), без
  классов и наследования.
- Публичная поверхность — только `window.OnBoard` с методами `start`, `stop`, `version`.
- Все слушатели событий снимаются при остановке тура; `ResizeObserver` и
  `MutationObserver` отключаются. Утечка наблюдателей на SPA накапливается молча.
- Логи — `console.debug` с префиксом `[OnBoard]`, и только их. Ни `console.log`,
  ни `console.error` на сайте клиента.

## 7. Тесты

- Имя теста описывает поведение: `test_foreign_project_returns_404`, а не `test_project_2`.
- Один тест проверяет одно утверждение. Длинные сценарные проверки — в e2e.
- Фикстуры данных — в `tests/factories.py`; тела тестов не заполняют БД вручную.
- E2E работают против стенда `testsite/`, никогда против внешних сайтов.
- Что покрываем обязательно, а что не покрываем — [workflow.md §6](workflow.md).
- Матрица изоляции арендаторов строится из таблицы маршрутов приложения, а не
  выписывается руками: новый приватный маршрут с идентификатором в пути попадает
  в проверку сам, а без записи о теле запроса тест полноты падает. Руками такая
  матрица устаревает на первом же добавленном эндпоинте.

## 8. Запрещено

- Добавлять зависимости вне списка в CLAUDE.md без согласования.
- Выполнять SQL в БД руками, в обход миграций.
- Использовать `innerHTML` для пользовательского контента.
- Коммитить `.env`, дампы БД, `node_modules`, артефакты сборки.
- Писать в БД события с IP, email или сырым User-Agent.
- Оставлять закомментированный код «на всякий случай» — для этого есть git.
- Рефакторить код, не относящийся к текущей задаче.
- Создавать абстракцию под одно использование.

## 9. Принципы и практики написания кода

Принципы проекта (KISS, YAGNI, MVP, Fail fast, итеративность) сформулированы в §1
[vision.md](vision.md) — там они про объём работ. Здесь — то же самое на уровне кода.

### 9.1 KISS и YAGNI в коде

- Самое простое решение, закрывающее задачу. Написал 200 строк там, где хватает 50 —
  перепиши.
- Абстракция появляется при **втором** использовании, параметр — при втором значении,
  обработка ошибки — при реальном, а не воображаемом сценарии.
- Никаких заготовок «на будущее»: ни пустых базовых классов, ни «пока не используемых»
  флагов, ни слоёв, через которые вызов просто проходит.

### 9.2 DRY по правилу трёх

Дублирование убираем на **третьем** повторении, не на втором. Два похожих куска кода
часто расходятся дальше, и преждевременное объединение склеивает то, что должно было
разойтись, — а разъединять потом дороже, чем было бы продублировать.

### 9.3 SOLID прагматично

Полезны всегда:

- **SRP** — у модуля одна причина для изменения. На практике: сервис не знает про HTTP,
  роутер не содержит бизнес-логики, виджет-модуль делает одно (`resolver` ищет элемент,
  `overlay` рисует, `engine` ведёт шаги).
- **DIP** — зависим от абстракции там, где реализация действительно подменяется:
  сервисы принимают `Session`, виджет принимает транспорт для событий (в тестах — фейк).

Остальные применяем **только когда задача об этом попросит**. Интерфейс под одну
реализацию, базовый класс с одним наследником и фабрика ради фабрики — это не OCP и не
ISP, а cargo cult, который запрещён §9.1.

### 9.4 Чистый код

- **Имена важнее комментариев.** `resolve_step_target` лучше, чем `handle` с
  пояснением. Переменные вроде `d`, `tmp`, `data2` не проходят ревью.
- **Функция решает одну задачу** и укладывается примерно в 30 строк. Длиннее — почти
  всегда внутри спрятаны две функции.
- **Вложенность до 3 уровней.** Глубже — ранние возвраты (`guard clauses`) вместо
  `else`.
- **Никаких магических чисел и строк:** `TARGET_WAIT_MS = 10_000` вместо `10000`
  в середине условия.
- **Один уровень абстракции внутри функции:** не смешиваем работу с SQL и формирование
  HTTP-ответа в одном теле.
- **Мёртвый код удаляется, а не комментируется.** История живёт в git.

### 9.5 Комментарии

Комментарий объясняет **почему**, а не **что**. Код уже говорит, что он делает.

Обязательны:

- над неочевидным решением — с причиной и ссылкой на ADR
  (`# Маска SVG, не z-index: ADR-0003`);
- над обходом чужого поведения (баг браузера, особенность Safari) — со ссылкой на
  источник;
- в docstring публичной функции сервиса — что она гарантирует и что поднимает.

Запрещены:

- пересказ кода (`# увеличиваем счётчик на единицу`);
- закомментированный код;
- `TODO` без указания задачи из tasklist.md.

### 9.6 README

README — часть задачи, а не отдельная работа «потом»:

- корневой `README.md` — что за проект, как поднять, где документы;
- `backend/README.md`, `panel/README.md`, `widget/README.md`, `testsite/README.md` —
  что внутри, как запустить и как протестировать именно этот компонент (нужны ещё и
  потому, что эти каталоги публикуются наружу отдельными репозиториями,
  [ADR-0007](adr/0007-monorepo-with-subtree-publishing.md));
- если задача изменила способ запуска, команду или переменную окружения — README
  правится в той же задаче. README, расходящийся с кодом, хуже отсутствующего.

### 9.7 Тесты — тоже код

К тестам применяются те же правила: имена по поведению, без дублирования подготовки
данных (фабрики в `tests/factories.py`), без закомментированных проверок. Что покрываем
обязательно — [workflow.md §6](workflow.md).

## 10. Чеклист перед сдачей задачи

Пробегается глазами по диффу, занимает минуту:

- [ ] дифф содержит только то, что требует задача
- [ ] нет «сирот»: неиспользуемых импортов, переменных, функций после моих правок
- [ ] имена говорят сами за себя, магических чисел нет
- [ ] функции в пределах ~30 строк, вложенность до 3 уровней
- [ ] абстракции нет там, где одно использование
- [ ] комментарии объясняют «почему», пересказа кода нет, `TODO` привязаны к задачам
- [ ] README компонента соответствует новому поведению
- [ ] ошибки API — в формате RFC 9457, коды из §4
- [ ] тесты есть и падают по делу, если убрать реализацию
- [ ] `make lint` и `make test` зелёные целиком
- [ ] ни один инвариант из CLAUDE.md не нарушен

## 11. Коммиты и CI

### 11.1 Conventional Commits

Формат сообщения — [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ru/v1.0.0/):

```
<тип>(<скоуп>)<!>: <описание до 72 символов>

<тело: что и почему, если из описания неочевидно>

Refs: T1.2
Co-Authored-By: …
```

**Типы** (закрытый список, проверяется хуком):

| Тип | Когда |
|---|---|
| `feat` | новая функциональность для пользователя |
| `fix` | исправление дефекта |
| `docs` | только документация |
| `style` | форматирование, без изменения поведения |
| `refactor` | изменение структуры кода без изменения поведения |
| `perf` | оптимизация |
| `test` | тесты |
| `build` | сборка, зависимости, Dockerfile |
| `ci` | конфигурация CI и хуков |
| `chore` | прочее, не влияющее на код продукта |
| `revert` | откат коммита |

**Скоупы:** `backend`, `panel`, `widget`, `testsite`, `e2e`, `docs`, `infra`, `deps`,
`repo`. Скоуп необязателен, но желателен — он сразу говорит, какой компонент затронут,
а это важно: компоненты публикуются наружу отдельными репозиториями
([ADR-0007](adr/0007-monorepo-with-subtree-publishing.md)).

`!` после скоупа — несовместимое изменение (для нас это прежде всего ломающее изменение
публичного API виджета, чего по §4 делать нельзя без крайней причины).

**Ссылка на задачу — футером `Refs: T1.2`**, а не в описании: так `git log --grep` ищет
по задаче, а описание остаётся читаемым. Один коммит на задачу (§5 workflow.md).

Примеры:

```
feat(widget): подсветка элемента SVG-маской

Маска вместо подъёма по z-index: ADR-0003.

Refs: T2.3
```

```
fix(backend): не писать query-строку URL в события

В параметрах встречаются токены и email, это PII (инвариант №7).

Refs: T4.1
```

### 11.2 Хуки

`.pre-commit-config.yaml`, ставятся один раз командой `make hooks`:

| Стадия | Что проверяет |
|---|---|
| `pre-commit` | пробелы в конце строк, перевод строки в конце файла, валидность YAML/JSON/TOML, конфликтные маркеры, регистр имён файлов, переводы строк LF, файлы крупнее 512 КБ, случайно закоммиченные приватные ключи |
| `pre-commit` | `ruff check --fix` и `ruff format` для `backend/` |

Версия `ruff` в `.pre-commit-config.yaml` и в `backend/pyproject.toml` **совпадает
точно**. Расхождение versions даёт противоречивые сигналы: хук правит файл одним
способом, `make lint` требует другого — проверено на 0.9.6 против 0.15.22, которые
по-разному сортируют импорты. При обновлении меняются оба места сразу.
| `commit-msg` | Conventional Commits (`conventional-pre-commit`, строгий режим) |

`pre-commit` живёт в корневом `.venv` — в системный Python его не поставить (PEP 668).
Разовая установка описана в `guides/local-setup.md`.

Фронтендовые хуки (`tsc --noEmit`, `vitest`) добавляются в конфиг тогда, когда у
`panel/` и `widget/` появится `package.json` — задачи T0.6 и T0.7. Раньше их добавлять
бессмысленно: хук без файлов только замедляет коммит.

### 11.3 CI

`.github/workflows/ci.yml`, пять задач, запускается на `push` в `main` и на
pull request:

| Задача | Что делает |
|---|---|
| `commits` | `scripts/check-commit-messages.sh` на диапазоне коммитов — защита истории от коммитов в обход хуков |
| `hooks` | `pre-commit run --all-files` — те же проверки, что локально |
| `backend` | `ruff check`, `ruff format --check`, `pytest` с сервисом `postgres:16-alpine` |
| `frontend` | `npm ci`, `tsc --noEmit`, `vitest`, бюджет размера бандлов |
| `e2e` | Playwright с Chromium, только на pull request |

Шаги условны по `hashFiles(...)`: пока компонента нет в репозитории, его шаг
пропускается, а не падает. Это сознательно — CI должен быть зелёным с первого дня,
иначе на него перестают смотреть.

Запустить CI может только владелец репозитория: нужен remote на GitHub. Я пишу и
валидирую конфигурацию, прогон — за вами (§3 [workflow.md](workflow.md)).

## 12. Правила, которые держат рост RPS

Из принципа «обратимость вместо запаса прочности» (§1 [vision.md](vision.md)).
Каждое правило стоит почти ноль сейчас и снимает будущее переписывание. Механизмы
под нагрузку (Redis, очередь, кэш, партиционирование) не строим, пока нагрузки нет.

### 12.1 Ресурсы с пулами — один раз на процесс

`AsyncEngine` и `httpx.AsyncClient` создаются в `lifespan` приложения и живут до
остановки. Создание движка или клиента на запрос — это новый TCP-коннект и новый
TLS-handshake на каждый вызов.

Параметры пула задаются явно, а не дефолтами:

```python
create_async_engine(
    settings.database_url,
    pool_size=10,          # базовых соединений на процесс
    max_overflow=10,       # временный запас на всплеск
    pool_timeout=5,        # сколько ждать соединение, прежде чем вернуть 503
    pool_recycle=1800,     # пересоздавать раз в 30 мин: pgbouncer и firewall рвут долгие
    pool_pre_ping=True,    # проверять живость перед выдачей
)
```

Дефолты молчаливы и неудобны: `pool_timeout` по умолчанию 30 секунд — под нагрузкой
это очередь запросов, висящих полминуты, вместо честного быстрого отказа.

### 12.2 Таймаут есть у каждого внешнего вызова

Ни одного обращения к сети или базе без таймаута. Конкретные значения для всех мест
системы — таблица §9.1 [vision.md](vision.md); там же правило вложенности: таймаут
вызывающей стороны всегда больше таймаута вызываемой. Вызов без таймаута под нагрузкой
превращается в утечку соединений.

### 12.3 Никаких сетевых вызовов внутри открытой транзакции

Транзакция удерживает соединение из пула. Обращение к Claude API внутри неё означает,
что соединение занято на время чужой задержки. Порядок всегда такой: прочитали данные →
закрыли транзакцию → сходили наружу → открыли новую транзакцию и записали.

### 12.4 Состояние дольше запроса — не в памяти процесса

Всё, что должно переживать запрос, живёт в БД. Единственное исключение — кэш, потеря
которого безвредна, и он всегда **за интерфейсом**, чтобы замениться на Redis без
правок вызывающего кода. Так сделан `RateLimiter` (§4.5 vision.md): in-memory сегодня,
Redis — когда появятся воркеры.

### 12.5 Event loop не блокируется

В `async def` нет синхронных обращений к сети и диску и нет CPU-тяжёлой работы.
Конкретный случай в нашем коде — **argon2**: хэширование пароля по своей природе
занимает десятки миллисекунд процессорного времени, и в async-обработчике его нужно
выносить в поток (`anyio.to_thread.run_sync`). Иначе каждый вход блокирует весь
процесс целиком.

### 12.6 Связи загружаются явно, N+1 запрещён

Ленивая загрузка в SQLAlchemy async по умолчанию недоступна — и это хорошо. Связи
грузятся через `selectinload`. На списковых эндпоинтах есть тест, считающий число
SQL-запросов: он фиксирует константу, а не «сколько получилось».

### 12.7 Горячий путь — только добавление и батчи

В приёме событий нет `SELECT` перед `INSERT` и нет `UPDATE`: дедупликация делается
`ON CONFLICT (event_id) DO NOTHING`, вставка — одним батчем на запрос. Любая проверка
«а нет ли уже такого» на горячем пути — это лишний round-trip на каждое событие.

### 12.8 Списковые ответы — всегда в конверте

Даже там, где сейчас десять записей: `{"items": [...], "next_cursor": null}`.
Добавить пагинацию потом — это изменение контракта и правка каждого потребителя;
отдать конверт сразу стоит одну строку. Максимальный размер страницы фиксирован.

### 12.9 Публичные ответы кэшируемы

`/v1/public/config` отдаётся с `ETag` и `max-age`, чтобы вынести его на CDN без
изменения контракта ([ADR-0009](adr/0009-widget-cache-and-versioning.md)).

### 12.10 Внешние точки входа идемпотентны

Приём событий — по `event_id` (инвариант №8). Это не только про дубли `sendBeacon`:
идемпотентность — предусловие для любой будущей очереди с повторной доставкой.

## 13. Конфигурация и секреты

Все настройки — через переменные окружения, читаются один раз в `core/config.py`
(pydantic-settings). `os.getenv` в коде приложения нет (§2).

Имена настроек приложения несут префикс **`ONBOARD_`**: в одном `.env` с ними живут
переменные compose (`POSTGRES_USER`, `TESTSITE_PORT`, `API_PORT`), и префикс разделяет
эти два набора.

| Переменная | Назначение | Отсутствует → |
|---|---|---|
| `ONBOARD_DATABASE_URL` | строка подключения `postgresql+psycopg://…` | приложение не стартует |
| `ONBOARD_JWT_SECRET` | подпись access-токенов | приложение не стартует |
| `ONBOARD_EDITOR_TOKEN_SECRET` | подпись токенов редактора (§9 data-model.md) | приложение не стартует |
| `ONBOARD_PUBLIC_API_URL` | адрес API, который подставляется в сниппет (`data-api`) | приложение не стартует |
| `ONBOARD_PANEL_ORIGIN` | origin панели для CORS приватного контура | приложение не стартует |
| `ONBOARD_LOG_LEVEL` | уровень логирования | `INFO` |
| `ONBOARD_ENV` | `dev` / `prod`: влияет на флаг `Secure` у cookie и на подробность ошибок | `dev` |

**Отсутствие секрета — отказ при старте, а не дефолтное значение.** Дефолтный
`JWT_SECRET` в коде — это подписанные предсказуемым ключом токены на продакшене;
такие дыры живут годами, потому что «и так работает». Это применение принципа
fail fast из §1 [vision.md](vision.md).

### 13.1 Единственная точка доступа к настройкам

`backend/app/core/config.py` — один класс и одна функция, больше настройки нигде не
читаются:

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_prefix="ONBOARD_",  # отделяет наши настройки от переменных compose
        env_file=".env",
        extra="ignore",   # см. ниже: почему не forbid
        frozen=True,      # настройки не меняются в рантайме
    )

    env: Literal["dev", "prod"] = "dev"
    log_level: Literal["DEBUG", "INFO", "WARNING", "ERROR"] = "INFO"

    # без значений по умолчанию — отсутствие валит старт
    database_url: PostgresDsn
    jwt_secret: SecretStr
    editor_token_secret: SecretStr
    public_api_url: AnyHttpUrl
    panel_origin: AnyHttpUrl

    # пул и таймауты — §9.1 vision.md
    db_pool_size: int = 10
    db_max_overflow: int = 10
    db_pool_timeout_s: int = 5
    db_pool_recycle_s: int = 1800
    db_statement_timeout_public_ms: int = 2_000
    db_statement_timeout_panel_ms: int = 5_000

    # сроки жизни токенов — ADR-0008, §9 data-model.md
    access_token_ttl_min: int = 15
    refresh_token_ttl_days: int = 30
    editor_token_ttl_min: int = 15


@lru_cache
def get_settings() -> Settings:
    return Settings()
```

Правила:

- **`SecretStr` для всех секретов.** Его `repr` печатает `**********`, поэтому секрет
  не утечёт ни в лог, ни в стектрейс, ни в вывод отладчика — прямая поддержка правила
  §9.3 vision.md о том, что токенов в логах не бывает.
- **Защита от опечаток — своя функция `unknown_settings_keys()`, а не `extra="forbid"`.**
  Проверено прогоном: `forbid` отвергает неизвестный ключ только в файле `.env`,
  переменную окружения `ONBOARD_JWT_SECRIT` он пропускает молча — и при этом
  отвергает чужие ключи из того же файла (`POSTGRES_USER`), то есть ломает запуск
  вне контейнера. Наша проверка смотрит и окружение, и файл, игнорирует чужие
  префиксы и валит старт с перечислением неизвестных имён.
- **Значения по умолчанию только у безопасных настроек.** У секретов и адресов их нет:
  pydantic поднимет `ValidationError` при старте.
- **Доступ через `get_settings()`** и зависимость FastAPI, а не через глобальную
  переменную модуля: так настройки подменяются в тестах переопределением зависимости.
- **Числа из таблиц §9.1 и §9.2 vision.md живут здесь**, а не литералами в коде
  (§9.4 — никаких магических чисел).
- В тестах настройки задаются переменными окружения или `get_settings` override,
  а не присваиванием полей.

Секреты не попадают ни в репозиторий, ни в логи, ни в сообщения об ошибках.
`.env.example` содержит имена переменных и примеры **нерабочих** значений.
`.env` в `.gitignore` с первого коммита.
