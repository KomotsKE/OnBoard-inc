## 1. Принципы разработки

Пять принципов, на которые ссылаемся в спорах о реализации. Они нужны не как лозунги,
а как критерий отклонения кода на ревью.

- **KISS.** Самое простое решение, закрывающее задачу. Если написано 200 строк там,
  где достаточно 50 — переписываем.
- **YAGNI.** Не пишем «на будущее». Абстракция появляется при втором использовании,
  настройка — при втором значении, обработка ошибки — при реальном, а не воображаемом
  сценарии.
- **MVP.** Объём первой версии ограничен §1.1 idea.md. Всё остальное — после приёмки.
- **Fail fast.** Бэкенд падает громко: валидация на входе, явные 4xx, никаких «тихих»
  дефолтов вместо ошибки конфигурации. Виджет — наоборот: падает тихо и не ломает сайт
  клиента (инвариант №1 в conventions.md). Это осознанная асимметрия: у бэкенда ошибку
  видим мы, у виджета — чужие пользователи.
- **Итеративность.** Каждая итерация из tasklist.md заканчивается состоянием, которое
  можно запустить и проверить. «Полуготовых» слоёв в репозитории не остаётся.
- **Обратимость вместо запаса прочности.** Закладываем то, что сейчас стоит почти ноль
  и задаёт границу: явные параметры пулов, таймауты, интерфейс вместо прямого вызова,
  конверт ответа с пагинацией, идемпотентность. Не строим механизмы, под которые нет
  нагрузки: кэш, очередь, шардирование. Проверка одна — **если нагрузка вырастет
  в 100 раз, это придётся переписать или просто донастроить?** Переписать — граница
  выбрана неверно, поправить сейчас. Донастроить — YAGNI работает, механизм ждёт своего
  времени. Правила, вытекающие отсюда, — §12 [conventions.md](conventions.md).

## 2. Стек

| Часть | Технологии | Почему так |
|---|---|---|
| Бэкенд | Python 3.12, FastAPI, **SQLAlchemy 2.0 async** (psycopg3), Alembic, PostgreSQL 16 | скорость написания CRUD + OpenAPI из коробки; async — чтобы потолком не стал threadpool и чтобы вызовы Claude API на этапе 7 не держали воркер ([ADR-0010](adr/0010-async-backend.md)) |
| Панель | React 18 + TypeScript, Vite, TanStack Query | типизированный контракт с API; серверное состояние не самописное |
| Виджет | TypeScript, сборка esbuild, **ноль рантайм-зависимостей** | бюджет 30 КБ gzip не оставляет места фреймворку; любая зависимость тянет свой рантайм на чужой сайт |
| Тесты | pytest + httpx, vitest, Playwright | по уровню: контракты, модули виджета, сквозные сценарии |
| Инфра | docker-compose (postgres, api, panel, testsite), Makefile | одна команда поднимает всё; переезд на сервер не меняет код |

Фиксированный набор зависимостей бэкенда и правило их добавления — в

### 4.2 Компоненты и ответственность

**`widget/loader.js`** — всё, что грузится синхронно в head клиента. Первое, что он
делает, — проверяет `window.OnBoard`: если виджет уже инициализирован, молча выходит.
Клиент вполне может вставить сниппет дважды (в шаблон страницы и в шаблон лэйаута),
а два оверлея поверх одного элемента — это поломка его сайта. Один запрос конфига,
проверка «есть ли что показывать», и только тогда подгрузка ядра. Ничего больше.
Цель — не замедлить сайт клиента, когда тура нет (а это 95% загрузок).

**`widget/core.js`** — движок тура:
- `ElementResolver` — находит элемент по селектору, ждёт его появления, проверяет
  видимость, следит за перемещением (ResizeObserver + rAF).
- `Overlay` — SVG-маска поверх страницы: затемнение с «окном» вокруг цели.
  Не трогает DOM клиента и его стили вообще.
- `Tooltip` — подсказка в Shadow DOM, собственное позиционирование с flip/shift.
- `TourEngine` — конечный автомат шагов, прогресс, условия показа.
- `Analytics` — буфер событий, отправка батчами и через `sendBeacon` при уходе.

**`widget/editor.js`** — отдельный бандл, грузится только в режиме настройки:
подсветка элемента под курсором, генерация устойчивого селектора, форма текста шага,
отправка шага в API.

**`backend/`** — FastAPI: публичный API для виджета (без авторизации, по public key),
приватный API для панели (JWT), агрегация аналитики.

**`panel/`** — React + TypeScript: авторизация, проекты, конструктор туров, брендинг,
дашборд аналитики.

Решения по UX виджета:
- подсветка — SVG-маска, а не манипуляция `z-index` элемента клиента (иначе ломается
  вёрстка и `position: sticky`);
- целевой элемент остаётся кликабельным — отверстие в маске не перехватывает события;
- `Esc` = «Пропустить», стрелки = навигация, фокус-трап внутри tooltip, `aria-live`
  для скринридеров;
- подсветка — **двойная обводка**: внешняя белая 3 px, внутренняя цветом бренда 2 px.
  Это следствие расчёта контраста, а не вкуса: `#2563EB` на затемнённом фоне даёт
  соотношение 1,09 — рамка одним брендовым цветом практически неразличима; белая
  обводка даёт 4,74 на светлом сайте и 18,9 на тёмном, то есть работает на любом;
- кнопка «Пропустить» видна всегда — это и честный UX, и источник метрики скипов.

### 4.5 Архитектура бэкенда

Поток запроса — один и тот же для всех приватных маршрутов:

```
HTTP
 │
 ▼ api/v1/panel/tours.py          async-роутер: разбор входа и вызов сервиса
 │   ├─ схема запроса (Pydantic)  невалидный вход → 422 автоматически
 │   └─ зависимости (core/deps.py)
 │        ├─ get_db            → AsyncSession из общего пула
 │        ├─ get_current_user  → user из JWT, иначе 401
 │        └─ get_owned_tour    → tour по id И user_id, иначе 404   (ADR-0006)
 ▼ services/tours.py              бизнес-логика: знает про AsyncSession, не про HTTP
 │   └─ поднимает NotFound / Conflict / ValidationError из core/errors.py
 ▼ models/tour.py                 SQLAlchemy 2.0, Mapped[...]
 ▼ PostgreSQL
```

**Слоёв ровно три: API — сервисы — модели.** Repository-слоя нет сознательно:
SQLAlchemy `Session` уже и есть Unit of Work с репозиториями, а обёртка над ней
добавила бы файлов, не добавив ни тестируемости (сервисы и так тестируются на
тестовой БД), ни развязки. Условие пересмотра: появление второго хранилища
(например ClickHouse для событий, §11) — тогда у `events` появится репозиторий,
но только у него.

**Транзакции.** Одна транзакция на запрос: `get_db` открывает `AsyncSession`, успешный
обработчик коммитит, исключение — откатывает. Сервисы **не коммитят** — иначе
нельзя собрать атомарную операцию из двух сервисов. Самый наглядный случай —
переупорядочивание шагов (T1.5): пересчёт `position` у всех шагов тура обязан быть
одним коммитом, иначе уникальность `(tour_id, position)` ломается на полпути.

Транзакция держится **коротко и без сетевых вызовов внутри**: обращение к внешнему API
при открытой транзакции удерживает соединение из пула на время чужой задержки —
классическая причина деградации под нагрузкой (§12 conventions.md).

**Ресурсы, живущие дольше запроса, создаются один раз в `lifespan`:** `AsyncEngine`
с явными параметрами пула и `httpx.AsyncClient` с таймаутами и лимитами. Движок или
клиент, создаваемый на каждый запрос, — это новый TCP-коннект и новый TLS-handshake
на каждый вызов; под нагрузкой это видно сразу.

**Ошибки.** Сервисы поднимают доменные исключения из `core/errors.py`
(`NotFoundError`, `ConflictError`, `ForbiddenOriginError`), один обработчик
исключений в `main.py` переводит их в HTTP и в формат
[RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457)
(`application/problem+json`):
`{"type": "/errors/tour-not-found", "title": "Тур не найден", "status": 404, "detail": "…"}`.
Машиночитаемый идентификатор — `type`; по `detail` логика не ветвится. Берём стандарт,
а не свой формат, потому что он уже решён и описан. `HTTPException` в сервисах не
встречается: это позволяет вызывать сервис из скрипта или из другого сервиса, не
втаскивая FastAPI.

**Два контура API с разными правилами.**

| | `api/v1/public/` (виджет) | `api/v1/panel/` (владелец) |
|---|---|---|
| Авторизация | `public_key` проекта + проверка `Origin` | JWT access-токен |
| CORS | любой Origin из `allowed_origins` проекта | только Origin панели, с `credentials` |
| Обратная совместимость | обязательна: на чужих сайтах живут старые версии скрипта, поля только добавляются | не требуется, панель деплоится вместе с API |
| Ответы | минимальные, кэшируемые (ETag на конфиге) | полные, без кэша |

**Приём событий** — отдельный путь без ORM-накладных: батч приходит одним запросом,
валидируется Pydantic, пишется одним `INSERT ... ON CONFLICT (event_id) DO NOTHING`.
Ответ всегда `204` при валидном ключе, даже если часть событий отброшена: виджет не
должен ретраить то, что не починится повтором.

**Аналитика** — один SQL с агрегатами в `services/analytics.py`. Цикл по событиям в
Python запрещён: на сотнях тысяч строк это единственное место, которое гарантированно
станет узким.

**Ограничения MVP, зафиксированные осознанно:**

- rate limit — in-memory token bucket по `public_key`, **за интерфейсом**
  `RateLimiter.allow(key) -> bool`. In-memory реализация корректна только при одном
  воркере uvicorn, поэтому в compose стоит один; переход на несколько воркеров — это
  вторая реализация того же интерфейса на Redis, без правок вызывающего кода. Сам Redis
  в MVP не поднимаем: механизма, под который нет нагрузки, не строим (§1);
- фоновых задач нет. Понадобится чистка событий по retention — это cron-контейнер в
  compose, а не Celery с брокером;
- `widget_last_seen_at` обновляется не чаще раза в 5 минут (`UPDATE ... WHERE
  widget_last_seen_at < now() - interval '5 minutes'`), иначе каждый просмотр страницы
  клиента порождал бы запись в БД.

```
src/api/client.ts     fetch-обёртка: базовый URL, Authorization, credentials,
                      единая обработка 401 → refresh → повтор запроса
src/api/tours.ts      функции на эндпоинт + типы ответов (зеркало схем бэкенда)
src/hooks/useTours.ts хуки TanStack Query с соглашением о ключах
```

`fetch` внутри компонента запрещён (conventions.md §5). Соглашение о ключах запросов:
`['projects']`, `['project', id]`, `['tours', projectId]`, `['tour', tourId]`,
`['analytics', tourId, range]` — от общего к частному, чтобы инвалидация по префиксу
работала предсказуемо: публикация тура инвалидирует `['tours', projectId]`, не весь кэш.

**Сессия.** Access-токен живёт в памяти `AuthProvider`, refresh — в httpOnly cookie
([ADR-0008](adr/0008-session-storage.md)). Отсюда три следствия в коде:

- при старте приложения и при F5 выполняется один `POST /v1/auth/refresh`; до его
  завершения рендерится сплэш, а не экран логина — иначе пользователя выкидывает
  на логин при каждом обновлении страницы;
- на 401 в `client.ts` запускается refresh, и **все** параллельные запросы ждут один
  и тот же промис (иначе пять одновременных запросов дадут пять refresh и гонку
  ротации токена), после чего повторяются один раз;
- выход — `POST /v1/auth/logout`, который гасит cookie на сервере; чистка памяти
  на клиенте сама по себе сессию не закрывает.

**Состояние.** Серверное — только TanStack Query, локальное — `useState`. Форма шага
в конструкторе — контролируемая, с явной кнопкой сохранения: автосохранение на каждый
символ дало бы запрос на каждое нажатие клавиши и мусор в истории.

**Переупорядочивание шагов** — `@dnd-kit/core` + `@dnd-kit/sortable`, оптимистично:
`onDragEnd` сразу меняет порядок в кэше Query и отправляет `PUT /tours/{id}/steps/order`;
ошибка откатывает кэш к предыдущему снимку. Порядок — это то, что пользователь видит
немедленно, ждать round-trip здесь неуместно.

**Превью подсказки** использует те же имена CSS-переменных, что и виджет
(`--onboard-primary`, `--onboard-radius`, …). Это не косметика: разойдясь, превью
начнёт врать про то, как подсказка выглядит на сайте.

**Единые состояния интерфейса.** Три компонента на весь проект — `<Loading/>`,
`<ErrorState/>`, `<Empty/>`; у каждого экрана обработаны все три. Белый экран при
ошибке запроса считается дефектом, а не «не дошли руками».

**Dev-окружение.** Vite проксирует `/v1` на `api:8000`, поэтому в разработке панель и
API — один origin, и cookie работает без дополнительных настроек. В собранном виде
панель отдаётся nginx-контейнером, адрес API берётся из переменной сборки.

## 5. Как работает editor-mode (выбор элемента на сайте клиента)

Это самая нетривиальная часть продукта. Альтернативы и почему отвергнуты:

| Вариант | Почему нет |
|---|---|
| Сайт клиента в `<iframe>` внутри панели | `X-Frame-Options: DENY` / `frame-ancestors` у большинства реальных сайтов. Неработоспособно без расширения браузера. |
| Браузерное расширение | Отдельный продукт, review в сторах, установка — убивает «10 минут до первого тура». |
| Только ручной ввод селектора | Противоречит цели «без разработчиков». Остаётся как fallback. |

**Выбранный вариант.** Виджет уже есть на сайте клиента. Он же умеет включать режим
редактора по специальной ссылке.

```
Панель: [🖱 Выбрать на сайте]
  │
  ├─▶ POST /api/v1/tours/{id}/editor-session        (JWT владельца)
  │     ← { url: "https://site.com/dashboard?onboard_edit=<token>", expires_in: 900 }
  │
  └─▶ window.open(url)  ─────────────────────────▶  САЙТ КЛИЕНТА
                                                     │ loader видит ?onboard_edit
                                                     │ GET /public/editor/session?token=…
                                                     │   ← { tour, steps, project }  (валиден 15 мин)
                                                     │ грузит editor.js
                                                     ▼
                                  mouseover → подсветка элемента + показ селектора
                                  click     → генерация селектора → форма шага
                                  «Добавить шаг» → POST /public/editor/steps (token)
                                  «Готово»  → закрыть вкладку
  ┌──────────────────────────────────────────────────┘
  ▼
Панель на window.focus перезапрашивает шаги → список обновился
```

Почему HTTP, а не `postMessage` между вкладками: cross-origin `window.opener` теряется
при навигации внутри сайта клиента (а она неизбежна — владелец ходит по своим страницам,
чтобы выбрать элементы на разных экранах). Через API состояние не зависит от живой связи
вкладок.

**Токен редактора.** Одноразово выдаваемый, TTL 15 минут, скоуп = один `tour_id`,
права = только чтение этого тура и создание/обновление его шагов. Утечка токена не даёт
доступа ни к панели, ни к другим проектам, ни к аналитике.

**Генерация устойчивого селектора** — по приоритету, первый подходящий и уникальный:

1. `[data-testid]`, `[data-qa]`, `[data-test]`, `[data-onboard-id]` — самые стабильные
2. `#id` — если id не выглядит сгенерированным (`/^[a-z][\w-]*$/i`, без длинных хэшей)
3. `[name]`, `[aria-label]`, `[role]` в сочетании с тегом
4. тег + «смысловые» классы (отфильтровав хэши CSS-модулей вида `css-1q2w3e`, `_btn_a1b2`)
5. короткий путь от ближайшего стабильного предка + `:nth-of-type`

Результат проверяется немедленно: селектор должен находить **ровно один** элемент на
текущей странице, иначе спускаемся на следующий уровень. В панели селектор остаётся
редактируемым вручную — автогенерация не обязана быть идеальной, она обязана быть
проверяемой.

## 6. Модель данных

```
users ──1:N── projects ──1:N── tours ──1:N── steps
  │              │                │
  │              └───────1:N──────┴──── events (append-only)
  └──1:N── refresh_sessions
```

| Сущность | Что хранит |
|---|---|
| `users` | владелец сайта: email и хэш пароля. Единственные персональные данные в системе |
| `refresh_sessions` | хэши refresh-токенов и цепочки ротации — состояние, без которого [ADR-0008](adr/0008-session-storage.md) не может обнаружить повторное использование украденного токена |
| `projects` | сайт клиента: `public_key`, разрешённые домены, тема оформления |
| `tours` | тур: статус, условие показа по URL, «показать один раз» |
| `steps` | шаг: порядок, селектор, тексты, положение подсказки |
| `events` | обезличенная телеметрия прохождения туров |

**Поля, типы, ограничения, индексы и объёмы — [data-model.md](data-model.md).**
Здесь остаются только решения, которые меняют архитектуру, а не схему.

**Тема оформления — один JSONB.** `{primary_color, text_color, backdrop_opacity,
border_radius, font_family, next_label, skip_label, done_label}` вместо десяти колонок:
набор настроек будет меняться, а запросов по отдельным полям темы не возникнет.
Валидация — в Pydantic.

**Каскадное удаление, без soft delete.** `ON DELETE CASCADE` по всей цепочке
user → projects → tours → steps и projects → events. Цена честная: удаление проекта с
миллионом событий даёт долгую транзакцию, поэтому в панели действие прячем за
подтверждением с вводом имени проекта. Soft delete протекает в каждую выборку и в каждую
формулу аналитики, а выигрыша в MVP не даёт.

**Хранение событий — 180 дней.** Политика зафиксирована, механизм чистки в MVP не
реализуем: чистить нечего, а индекс для неё уже есть. Когда понадобится — это
cron-контейнер из §4.5, не планировщик задач.

**Идентификация посетителя.** `visitor_id` — анонимный uuid из localStorage на сайте
клиента, не привязанный к личности. Ключ хранения включает `public_key`:
`onboard.v1.<public_key>.visitor`. Без этого два наших клиента на поддоменах одного
домена делили бы один идентификатор посетителя и портили друг другу аналитику.

**Отбор тура выполняется в SQL, а не в Python.** Режим `regex` — это выражение,
которое написал владелец сайта. В Python катастрофический бэктрекинг заблокировал бы
event loop без всякого предела: таймаута у модуля `re` нет. В PostgreSQL то же
выражение обрывает `statement_timeout` публичных маршрутов (2 с), поэтому сравнение
отдано базе — `starts_with`, `strpos` и оператор `~`. Обратная сторона: синтаксис
POSIX-выражений PostgreSQL не совпадает с Python, поэтому выражение при сохранении
тура проверяется той же машинкой, которая будет его применять.

**Условие показа тура сравнивается с `pathname + search`.** Не с полным URL:
`origin` уже проверен через `allowed_origins`, а `hash` в SPA меняется произвольно и
ломал бы условие. Перед сравнением убирается завершающий слэш (`/pricing/` и
`/pricing` — одна страница). Регистр значим: по RFC 3986 путь регистрозависим, и
`/Pricing` — другой адрес.

**Что мы не храним о конечных пользователях:** ни IP, ни сырой User-Agent, ни
query-строку URL, ни содержимое DOM сайта клиента. Полный список и обоснования —
§2 data-model.md.

**Почему PostgreSQL, а не ClickHouse.** На горизонте MVP объём событий — единицы
миллионов строк; `GROUP BY` по индексу отвечает за десятки миллисекунд. Отдельное
аналитическое хранилище — это +1 сервис в docker-compose, +1 источник правды и
несогласованность на старте. Расчёт объёмов — §7 data-model.md, путь масштабирования —
§11 и [ADR-0005](adr/0005-postgres-for-events.md).

## 7. Событийная модель и аналитика

### 7.1 События

| Событие | Когда | Полезная нагрузка |
|---|---|---|
| `tour_started` | показан первый шаг | `run_id`, `url` |
| `step_viewed` | показан шаг N | `step_id`, `step_position` |
| `step_back` | нажал «Назад» | `step_id` |
| `tour_skipped` | «Пропустить» / `Esc` | `step_id` — где именно бросил |
| `tour_completed` | «Готово» на последнем шаге | `run_id` |
| `step_target_missing` | элемент не найден за 10 с | `step_id`, `selector` |
| `widget_error` | перехвачено исключение в коде виджета | `code`, `step_id` (если есть) |
| `widget_ping` | первая загрузка на домене | — (для статуса «подключён») |

`run_id` — uuid одного прохода тура, генерируется при `tour_started`. Вся воронка
считается по `run_id`; `visitor_id` нужен только для «не показывать повторно» и для
различения уникальных пользователей.

`widget_error` — единственный способ узнать, что виджет падает у клиента: консоль его
браузера нам недоступна, а по инварианту №1 мы гасим исключения молча. Отправляем код
ошибки и номер шага — без стектрейсов, без содержимого страницы, без параметров URL.

Коды закрытым списком, новые только добавляются:

| Код | Когда |
|---|---|
| `target_timeout` | элемент шага не появился за 10 с (дубль `step_target_missing` на уровне ошибок) |
| `config_fetch_failed` | конфиг не получен: сеть, CORS, 5xx |
| `render_failed` | исключение при построении оверлея или подсказки |
| `storage_unavailable` | localStorage недоступен или выбрасывает исключение |
| `unexpected` | всё, что не подошло под перечисленное |

**`device` определяется возможностями браузера, а не разбором User-Agent.** Виджет
считает его сам: `matchMedia('(pointer: coarse)')`, `matchMedia('(hover: hover)')` и
ширина экрана дают `desktop | mobile | tablet`. User-Agent не разбирается и на сервер
не отправляется вовсе — по рекомендации MDN «проверяй возможность, а не браузер», и
заодно это снимает тему отпечатка браузера.

Разбивки по браузерам в MVP нет: надёжно определить браузер без разбора UA нельзя
(User-Agent Client Hints поддерживает только Chromium), а колонка, в которой у
половины посетителей стояло бы `other`, не стоит ни строки кода. Ни один критерий
оценки этого не требует.

### 7.2 Метрики и их формулы

Считаем честно и однозначно, чтобы цифры в панели не вызывали вопросов:

```
Запуски            = COUNT(DISTINCT run_id) WHERE type='tour_started'
Завершения         = COUNT(DISTINCT run_id) WHERE type='tour_completed'
Скипы              = COUNT(DISTINCT run_id) WHERE type='tour_skipped'
Completion rate    = Завершения / Запуски
Skip rate          = Скипы  / Запуски
Брошено без явного
скипа (dropped)    = Запуски − Завершения − Скипы      (закрыл вкладку)
Воронка шага N     = COUNT(DISTINCT run_id) WHERE type='step_viewed' AND step_position=N
Drop-off шага N    = 1 − Воронка(N+1) / Воронка(N)
Проблемный шаг     = argmax Drop-off  (подсвечиваем в UI)
```

Три числа из критериев оценки — «запуски», «скипы», «% дошедших до финала» — это
первые строки этого списка. Воронка по шагам — то, что делает их полезными:
без неё владелец знает, что тур плохой, но не знает, где именно.

**Период — скользящее окно.** «7 дней» означает `created_at >= now() - interval
'7 days'`; все метки времени — `timestamptz` в UTC. Календарных дней и таймзоны
владельца в MVP нет: это отдельная работа и постоянный источник расхождений вида
«почему за сегодня ноль, а на графике двенадцать». Граница периода одинакова для
тоталов и для воронки — иначе суммы не сойдутся между блоками одного экрана.

### 7.4 Доставка событий

- буфер в памяти, флаш батчем раз в 3 с или при 10 событиях;
- `visibilitychange: hidden` → `navigator.sendBeacon` (работает при закрытии вкладки);
- не доставленный батч → localStorage, повтор при следующей загрузке (TTL 24 ч);
- эндпоинт `POST /v1/public/events` принимает массив, отвечает `204` **всегда** при
  валидном ключе (виджет не должен ничего ретраить по ошибкам схемы), пишет батчем
  с `ON CONFLICT (event_id) DO NOTHING`;
- rate limit по `public_key` и IP: 100 запросов/мин — защита от случайного шторма; при превышении 429 с `Retry-After`, полная таблица политик — §9.2.

## 8. API

### 8.1 Публичный API (виджет, CORS, авторизация по public key)

```
GET  /v1/public/config?key=pk_…&url=/reports?plan=pro
     → 200 { core_url: "https://…/core.<hash>.js",
             project: {theme}, tour: {id, name, show_once, steps:[…]} | null }
     Один запрос — всё, что нужно для показа. ETag, max-age=60; If-None-Match
     даёт 304. Кэш экономит трафик, а не запросы к базе: чтобы узнать текущий
     ETag, тур всё равно нужно отобрать (выносится на CDN — экономит и их).
     core_url — точный адрес ядра с хэшем сборки, имя файла берётся из
     manifest.json сборки виджета (ADR-0009). Нет манифеста → 503: это отказ
     развёртки, и он должен быть виден в логах, а не выглядеть как «нет тура».
     url — pathname + search, а не полный href: hash в сравнении не участвует,
     и передавать его нашему API незачем. Абсолютный адрес тоже принимается.
     Origin проверяется против allowed_origins; пустой список = ни один домен
     не разрешён (fail closed): виджет молчит, в панели горит подсказка
     «добавьте домен». Fail open был бы дырой — чужой сайт смог бы
     воспользоваться ключом.
     Успешный ответ несёт Access-Control-Allow-Origin с проверенным доменом
     (не `*`) и Vary: Origin. На ответах с ошибкой заголовков CORS нет: виджет
     одинаково молчит при любом отказе и тела ошибки не читает.

POST /v1/public/events          { key, events: [ {event_id, type, …} ] } → 204

GET  /v1/public/editor/session?token=…   → 200 { tour, steps, theme }
POST /v1/public/editor/steps             { token, step } → 201 { step }
PATCH/DELETE /v1/public/editor/steps/{id}
```

```

       → 200 { access_token, expires_in } + Set-Cookie: onboard_rt=… (httpOnly, Secure,
         SameSite=Lax, Path=/v1/auth)
POST   /v1/auth/refresh    по cookie, без тела → 200 { access_token, expires_in }
POST   /v1/auth/logout     гасит cookie на сервере → 204
GET    /v1/me

GET    /v1/projects                 POST /v1/projects
GET    /v1/projects/{id}            PATCH /v1/projects/{id}      (name, allowed_origins, theme)
DELETE /v1/projects/{id}            каскадом уносит туры, шаги и события проекта
GET    /v1/projects/{id}/snippet    → готовый <script> для вставки

GET    /v1/projects/{id}/tours      → [{ …тур, runs_7d, completion_rate_7d }]
                                      агрегаты за 7 дней одним GROUP BY: список туров
                                      показывает метрики без запроса на каждый тур
POST   /v1/projects/{id}/tours
GET    /v1/tours/{id}               → тур вместе со шагами, одним запросом
PATCH/DELETE /v1/tours/{id}
POST   /v1/tours/{id}/publish  |  /v1/tours/{id}/unpublish
       публикация тура без шагов → 422 (иначе клиент получит «работающий» тур,
       который ничего не показывает); архивный тур виджету не отдаётся, но его
       аналитика остаётся доступной.
       Удаление последнего шага опубликованного тура не запрещаем, но оно
       автоматически снимает тур с публикации: ответ DELETE /steps/{id} содержит
       новый статус тура, панель сообщает об этом явно. Запрет удаления выглядел бы
       произвольным, а опубликованный тур без шагов — хуже
POST   /v1/tours/{id}/editor-session   { mode: "edit" | "preview" }
                                       → { url, expires_in }
       mode=preview — проход тура без записи событий, иначе прогоны владельца
       портят его же воронку

POST   /v1/tours/{id}/steps         PATCH/DELETE /v1/steps/{id}
PUT    /v1/tours/{id}/steps/order   { step_ids: [...] }

GET    /v1/tours/{id}/analytics?range=7d|30d
       → { totals: {...}, funnel: [{step_position, title, runs, rate}], issues: [...] }
       скользящее окно в UTC (§7.2); календарных периодов и таймзон в MVP нет
```

Какой экран вызывает какой эндпоинт и какие поля показывает —
[screens.md](screens.md). Эндпоинтов без потребителя в контракте нет: это проверено
сверкой (§6 того же документа).

Многопользовательность: каждый приватный запрос фильтруется по `user_id` из JWT на
уровне запроса к БД. Никакого «проверим права потом» — изоляция арендаторов входит в
слой доступа к данным с первого коммита.

| Доступность | фокус-трап, `Esc`, `aria-*`, контраст ≥ 4.5:1 | axe-core в тестах |

Серверных запросов по этому URL мы не делаем — его открывает браузер владельца, поэтому SSRF-поверхности нет | чужой `project_id` → 404; 11-я попытка логина с одного IP → 429; 6-я неудачная по одному email → 429; URL редактора с `file://` или чужим origin → 422 |

Последняя строка про try/catch — главное правило виджета: **мы работаем на чужом

это инцидент у клиента.

### 9.1 Таймауты

Ни одного ожидания без предела. Значения выбраны так, чтобы **вложенность соблюдалась**:
таймаут вызывающей стороны всегда больше таймаута вызываемой, иначе клиент отвалится
раньше, чем сервер успеет вернуть осмысленную ошибку, и вместо диагностируемого отказа
мы получим тишину.

| Где | Значение | Что происходит при истечении |
|---|---|---|
| `statement_timeout`, публичные маршруты | 2 с | запрос прерывается, ответ 503 `problem+json`; виджет уходит в буфер и повторит |
| `statement_timeout`, маршруты панели | 5 с | 503, панель показывает `<ErrorState/>` с кнопкой «повторить» |
| `pool_timeout` (ожидание соединения) | 5 с | 503 «сервис занят» — быстрый честный отказ вместо очереди |
| `pool_recycle` | 1800 с | соединение пересоздаётся; защита от молчаливых обрывов на firewall и pgbouncer |
| `httpx`: connect / read / write / pool | 2 / 10 / 5 / 2 с | исключение в сервисе → 502 `problem+json`. Для Claude API на этапе 7 `read` пересматривается отдельно |
| uvicorn keep-alive | 5 с | праздное соединение закрывается, не занимая воркер |
| uvicorn graceful shutdown | 20 с | незавершённые запросы добиваются, потом процесс гасится |
| Виджет: загрузка конфига (`AbortController`) | 3 с | тур не показывается, событие `widget_error` с кодом `config_fetch_failed`; **повтора в этой загрузке страницы нет** — иначе медленный бэкенд получит шторм ретраев |
| Виджет: отправка батча событий | 5 с | батч остаётся в буфере и уедет при следующем флаше или загрузке |
| Виджет: ожидание элемента шага | 10 с | `step_target_missing`, тур корректно закрывается (§3.3 idea.md) |
| Токен редактора | 15 мин | 401, панель предлагает открыть сайт заново ([ADR-0004](adr/0004-editor-mode-over-http.md)) |
| Access-токен / refresh-токен | 15 мин / 30 дней | прозрачное обновление в `api/client.ts` ([ADR-0008](adr/0008-session-storage.md)) |

Проверяется тестами: запрос с искусственной задержкой в БД прерывается по
`statement_timeout`, а не висит; виджет при недоступном API прекращает попытки
(T2.1, T2.8).

### 9.2 Ограничение частоты запросов

Лимитер один — интерфейс `RateLimiter.allow(bucket, limit, window) -> Decision`
(§4.5), политики разные. Ключ bucket'а подобран так, чтобы один шумный клиент не
выключал сервис остальным.

| Что защищаем | Ключ | Лимит | Ответ при превышении |
|---|---|---|---|
| `POST /v1/public/events` | `public_key` + IP | 100 запросов / мин | 429 + `Retry-After`; виджет держит события в буфере и повторяет с экспоненциальной задержкой |
| `GET /v1/public/config` | `public_key` + IP | 120 запросов / мин | 429 + `Retry-After`; виджет не показывает тур и не ретраит в этой загрузке |
| `POST /v1/auth/login` | IP | 30 попыток / 5 мин | 429 + `Retry-After` |
| `POST /v1/auth/login` | email (нормализованный) | 5 неудачных попыток / 15 мин | 429 независимо от IP — иначе подбор пароля к конкретному аккаунту идёт с распределённых адресов |
| `POST /v1/auth/register` | IP | 10 регистраций / час | 429 |
| `POST /v1/auth/refresh` | IP | 60 запросов / мин | 429 |
| Публичные маршруты редактора | токен редактора | 60 запросов / мин | 429 |
| Все маршруты панели | `user_id` | 600 запросов / мин | 429 — защита от зацикленного фронтенда, а не от злоумышленника |

Двойная защита логина (по IP и по email) — отдельное требование, а не перестраховка:
лимит только по IP не мешает подбирать пароль к одному аккаунту с множества адресов,
а лимит только по email позволяет перебирать аккаунты с одного адреса.

Лимит по IP широкий сознательно. За одним адресом сидит целый офис за NAT, и десяток
попыток на всех — это отказ в обслуживании собственным клиентам; подбор пароля он всё
равно не останавливает (30 попыток за 5 минут против пароля от 15 символов — ничто).
Останавливает подбор лимит по email: пять неудач за 15 минут. Первым на этот перекос
напоролся наш же набор e2e-сценариев (T3.4) — ровно так же на него напоролся бы
клиент с несколькими сотрудниками. Это также
закрывает требование NIST SP 800-63B-4 о throttling попыток аутентификации (§5.1
[data-model.md](data-model.md)).

Формат ответа — `problem+json` с `type: "/errors/rate-limited"` и заголовком
`Retry-After` в секундах. Заголовки черновика `RateLimit-*` не добавляем: единственный
потребитель — наш собственный виджет, которому достаточно `Retry-After`.

Счётчики живут в in-memory реализации лимитера, то есть при одном воркере. Это
записанное ограничение MVP (§4.5), а не недосмотр: подмена на Redis — вторая
реализация интерфейса.

### 9.3 Логирование и диагностика

Тоже «закладываем сразу»: без идентификатора запроса в логах под нагрузкой невозможно
связать между собой записи одного вызова, а добавить его потом — значит переписать
каждое место логирования.

- **Формат — JSON, одна строка на запись**, в stdout. Контейнер не пишет файлов: логи
  собирает тот, кто его запустил.
- **`request_id`** берётся из заголовка `X-Request-Id`, если он пришёл, иначе
  генерируется; возвращается в ответе тем же заголовком и присутствует в каждой записи
  лога этого запроса.
- **Обязательные поля:** `ts`, `level`, `request_id`, `method`, `path`, `status`,
  `duration_ms`; для приватных маршрутов — `user_id`, для публичных — `project_id`.
- **Уровни:** `INFO` — завершение запроса; `WARNING` — ожидаемые отказы (429, 403,
  истёкший токен); `ERROR` — необработанное исключение и 5xx, со стектрейсом.
  Записи на каждый успешный `SELECT` нет: логи — не журнал SQL.
- **Что не попадает в логи никогда:** пароли и хэши, access- и refresh-токены, токены
  редактора, `Set-Cookie`, тела событий целиком. Токен в логе — это утечка, живущая
  столько же, сколько лог.
- Виджет на сайте клиента пишет только в `console.debug` с префиксом `[OnBoard]`
  (§6 conventions.md): чужая консоль — не наше место для диагностики.

**Журнал значимых операций.** Кроме записи о завершении запроса логируется каждая
операция, изменяющая состояние или относящаяся к безопасности. Имя события — точечное,
чтобы по нему можно было фильтровать; запись делается **после успешного коммита**,
иначе лог сообщит о том, что откатилось.

| Событие | Уровень | Поля сверх обязательных |
|---|---|---|
| `app.started` | INFO | версия, параметры пула, `env` |
| `app.stopping` | INFO | — |
| `migrations.applied` | INFO | ревизия |
| `user.registered` | INFO | `user_id` |
| `user.login.success` | INFO | `user_id` |
| `user.login.failed` | WARNING | причина (`unknown_email` / `bad_password`), **без email и без IP** |
| `user.logout` | INFO | `user_id` |
| `auth.refresh.rotated` | INFO | `user_id`, `family_id` |
| `auth.refresh.reuse_detected` | ERROR | `user_id`, `family_id` — признак кражи токена, вся цепочка погашена |
| `project.created` / `.updated` / `.deleted` | INFO | `project_id` |
| `tour.created` / `.published` / `.unpublished` / `.deleted` | INFO | `tour_id`, предыдущий и новый статус |
| `tour.auto_unpublished` | WARNING | `tour_id` — снят с публикации удалением последнего шага (§8.2) |
| `step.created` / `.updated` / `.deleted` | INFO | `tour_id`, `step_id` |
| `steps.reordered` | INFO | `tour_id`, число шагов |
| `editor_session.issued` | INFO | `tour_id`, `mode` (`edit` / `preview`) |
| `editor_session.rejected` | WARNING | причина (`expired` / `foreign_tour`) |
| `widget.first_seen` | INFO | `project_id` — первое подключение виджета на проекте |
| `widget.config.forbidden_origin` | WARNING | `project_id` — домена нет в `allowed_origins`; в панели это та самая подсказка «добавьте домен» |
| `events.batch_accepted` | INFO | `project_id`, принято, отброшено дублей |
| `events.batch_rejected` | WARNING | `project_id`, причина (`forbidden_origin` / `rate_limited`) |
| `rate_limit.exceeded` | WARNING | бакет, `project_id` или `user_id` — **без IP** |

IP в журнал не попадает даже там, где он является ключом лимита: инвариант №7 не знает
исключений, а для разбора инцидента достаточно `project_id` и бакета.

Метрик, трассировки и внешнего сборщика в MVP нет — это механизмы, под которые нет
нагрузки (§1). JSON выбран именно для того, чтобы подключить сборщик потом без правок
кода.

| Рост объёма событий | низкая на MVP | среднее | путь масштабирования описан, решение не принимаем заранее |

## 11. Путь масштабирования (не делаем сейчас, но не отрезаем)

Решения MVP выбраны так, чтобы их можно было заменить, не переписывая продукт:

- **События**: ingest уже принимает батчи и идемпотентен → при росте между API и БД
  встаёт очередь (Redis Stream / Kafka), события уезжают в ClickHouse, панель читает
  из предагрегатов. Контракт `POST /public/events` не меняется.
- **Конфиг виджета**: отдельный `GET` с ETag → выносится на CDN как статический JSON,
  публикация тура инвалидирует кэш.
- **Статика виджета**: уже отдельные файлы с хэшем в имени → любой CDN.
- **Туры**: `url_match` и `show_once` — заготовка под полноценный таргетинг
  (сегменты, частота, A/B) без миграции схемы шагов.

## 12. Где в платформу встраивается AI (детали — следующий документ)

Фиксирую точки подключения, чтобы модель данных их выдержала; реализация обсуждается
на шаге 2:

1. **Генерация тура** — по URL страницы и её DOM-скелету модель предлагает 3–5 шагов
   с селекторами и текстами; владелец правит. Это бьёт прямо в метрику
   «10 минут до первого тура».
2. **Переписывание текстов** — «короче», «дружелюбнее», «в tone of voice бренда»,
   перевод на другие языки.
3. **Самовосстановление селекторов** — при `step_target_missing` модель сопоставляет
   сохранённый контекст элемента (`selector_candidates`, текст, роль) с текущим DOM и
   предлагает новый селектор. Поле `selector_candidates` в схеме — задел именно под это.
4. **Объяснение воронки** — по данным аналитики текстовая гипотеза, почему теряются на
   шаге N, и что поправить.
