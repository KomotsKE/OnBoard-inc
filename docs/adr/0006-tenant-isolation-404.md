# ADR-0006: Изоляция арендаторов в слое запроса, чужой объект → 404

Статус: принято · Дата: 2026-10-12 · Задачи: T1.3

## Контекст

Платформа многопользовательская: у каждого владельца свои проекты, туры и аналитика.
Утечка данных между арендаторами — самый дорогой класс дефектов: он не проявляется
в обычном использовании и обнаруживается уже как инцидент.

## Решение

Доступ к объектам панели идёт только через зависимости `get_owned_project` /
`get_owned_tour`, которые подставляют `user_id` из JWT **в сам SQL-запрос**
(`WHERE id = :id AND user_id = :uid`). Объект, не принадлежащий пользователю, не
выбирается вовсе, и обработчик отвечает **404**.

Тест на изоляцию — обязательная часть задачи, вводящей новый приватный маршрут:
матрица «2 пользователя × 2 проекта × все маршруты».

## Альтернативы и почему отвергнуты

- **Выбрать объект, затем сравнить владельца и вернуть 403.** Работает, но
  во-первых, легко забыть проверку в новом обработчике (ошибка «по умолчанию
  открыто»), во-вторых, 403 подтверждает существование объекта с таким id, что
  позволяет перебором узнать чужие идентификаторы.
- **Row-level security в PostgreSQL.** Надёжнее, но требует проброса пользователя
  в сессию соединения и усложняет пул соединений и тесты — непропорционально
  объёму MVP.
- **Проверка в middleware по шаблону URL.** Хрупко: ломается при любом изменении
  схемы маршрутов и не покрывает вложенные ресурсы.

## Последствия

- Любой новый приватный эндпоинт обязан получать объект через эти зависимости;
  прямой `session.get(Project, id)` в обработчиках панели запрещён.
- Ответ 404 вместо 403 немного усложняет отладку («не найден» вместо «нет прав») —
  компенсируется логом с `user_id` и `object_id` на уровне debug.
