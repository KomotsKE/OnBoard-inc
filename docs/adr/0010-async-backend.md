# ADR-0010: Асинхронный бэкенд

Статус: принято · Дата: 2026-10-13 · Отменяет: выбор sync-стека в §2 vision.md ·
Задачи: T0.3, T0.5, этап 1

## Контекст

Изначально в §2 vision.md был зафиксирован синхронный SQLAlchemy с обоснованием
«нагрузка MVP не требует async-сложности». Для объёма MVP это верно.

Требование изменилось: платформа должна выдерживать рост RPS **без переписывания
ядра**. Это меняет оценку, потому что синхронный путь упирается не в базу:
FastAPI выполняет синхронные обработчики в threadpool (по умолчанию 40 воркеров),
и при высоком RPS потолком становится он. Один медленный запрос к базе занимает поток
целиком.

Отдельно важен этап 7: AI-слой ходит в Claude API, а это сетевые вызовы на секунды.
В синхронном обработчике такой вызов держит поток из threadpool всё это время.

Переход sync → async позже — не донастройка: меняются подписи всех сервисов, все
зависимости FastAPI и все тесты. Это ровно тот случай, который требование запрещает.

## Решение

Бэкенд асинхронный с первого коммита:

- обработчики — `async def`;
- SQLAlchemy 2.0 в асинхронном режиме: `create_async_engine`, `AsyncSession`,
  драйвер `postgresql+psycopg://` (psycopg3 умеет async, отдельный драйвер не нужен);
- внешние HTTP-вызовы — `httpx.AsyncClient`, один на процесс, создаётся в `lifespan`;
- тесты — `pytest-asyncio`, клиент `httpx.ASGITransport`;
- Alembic остаётся синхронным: миграции запускаются отдельным процессом, async там
  не нужен и только усложнил бы `env.py`.

## Альтернативы и почему отвергнуты

- **Остаться на sync.** Проще писать и отлаживать, быстрее к MVP. Отвергнуто
  требованием: потолок threadpool и блокирующие вызовы к Claude API — это будущее
  переписывание всего слоя доступа к данным.
- **Async только на горячих путях** (`/public/config`, `/public/events`), панель —
  sync. Горячих путей действительно два, но цена — два стиля в одном проекте, два
  набора фикстур и постоянный вопрос «а здесь какой?». Непропорционально выигрышу.
- **Sync + много воркеров uvicorn.** Работает до определённого предела, но умножает
  потребление памяти и соединений с базой: каждый воркер держит свой пул.

## Последствия

- **Блокирующий вызов в `async def` останавливает весь event loop.** Это новый класс
  ошибок, которого в sync-коде нет. Правило в §12 conventions.md: никаких
  синхронных обращений к сети, диску и CPU-тяжёлых операций в обработчике; тяжёлое —
  через `run_in_executor` или отдельный процесс.
- Ленивая загрузка связей в SQLAlchemy async запрещена по умолчанию — связи
  загружаются явно (`selectinload`). Это скорее плюс: N+1 перестаёт возникать молча.
- Отладка сложнее: стектрейсы длиннее, падения в задачах нужно явно ожидать.
- `pytest-asyncio` добавляется в dev-зависимости; все тесты API — асинхронные.
- Пулы соединений начинают работать нативно, без обходных путей — что и было целью.
