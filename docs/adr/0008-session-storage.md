# ADR-0008: Access-токен в памяти SPA, refresh — в httpOnly cookie

Статус: принято · Дата: 2026-10-12 · Задачи: T1.1, T3.1

## Контекст

Панель — SPA, которая работает с данными владельцев сайтов: туры, аналитика, ключи
проектов. Угроза, от которой защищаемся, — XSS в самой панели: достаточно одной
уязвимости (сторонняя зависимость, вставка неэкранированного текста тура), чтобы
скрипт атакующего прочитал всё, что доступно JS.

## Решение

- **Access-токен** (TTL 15 минут) возвращается в теле ответа и хранится только
  в памяти `AuthProvider`. В `localStorage` и `sessionStorage` не попадает.
- **Refresh-токен** (TTL 30 дней) ставится сервером как cookie
  `httpOnly; Secure; SameSite=Lax; Path=/v1/auth`. JS его не видит в принципе.
- Маршруты: `POST /v1/auth/login|register` выдают пару, `POST /v1/auth/refresh`
  работает по cookie без тела, `POST /v1/auth/logout` гасит cookie на сервере.
- При старте приложения и после F5 выполняется один `refresh`; до его завершения
  показывается сплэш, а не экран логина.
- На 401 все параллельные запросы ждут один общий промис refresh и повторяются
  однократно.

## Альтернативы и почему отвергнуты

- **Оба токена в `localStorage`.** Проще всего и переживает перезагрузку само собой,
  но любой XSS уводит долгоживущий refresh-токен — то есть доступ к аккаунту
  надолго, а не на 15 минут. Разница в цене — около 40 строк кода, разница в
  последствиях — несопоставима.
- **Оба токена в cookie + CSRF-токен.** Безопасно и привычно, но добавляет CSRF-контур
  на все пишущие запросы, усложняет отладку и плохо совмещается с планом отдать панель
  и API с разных доменов.
- **Серверные сессии в БД.** Снимает вопросы с токенами, но добавляет запрос к БД на
  каждый вызов API и таблицу сессий — непропорционально объёму MVP.

## Последствия

- `SameSite=Lax` и `Path=/v1/auth` означают: cookie уходит только на маршруты
  аутентификации и только с нашего сайта. В dev это работает потому, что Vite
  проксирует `/v1` на бэкенд и origin один; в прод панель и API должны быть на одном
  домене (или на поддоменах с общим родителем), иначе потребуется
  `SameSite=None; Secure` и честный CORS с `credentials`.
- `Secure` ломает работу по `http://` где-либо, кроме `localhost`. Для стенда это
  допустимо, для сервера — требует TLS с первого дня.
- Refresh-токен ротируется при каждом использовании; старый становится недействительным.
  Повторное использование старого токена — сигнал кражи, такая сессия закрывается.
- Обязательные тесты: refresh по cookie без заголовка; повторное использование
  ротированного токена → 401; logout делает cookie непригодной; пять параллельных
  401 дают ровно один refresh (тест на панели).
