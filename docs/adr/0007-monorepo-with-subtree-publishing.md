# ADR-0007: Монорепозиторий с публикацией поддеревьев в отдельные репозитории

Статус: принято · Дата: 2026-10-12 · Задачи: T0.1, T0.10

## Контекст

Разработка ведётся в одном рабочем каталоге, но наружу бэкенд и панель должны
существовать как отдельные репозитории. Названные причины: разные деплои и CI, а также
разграничение ответственности между людьми, работающими над частями проекта.

При этом проект содержит кросс-компонентные артефакты, у которых нет естественного
«владельца» среди двух репозиториев: `docs/`, `CLAUDE.md`, `docker-compose.yml`,
`Makefile`, `testsite/`, `e2e/`. Часть задач из tasklist.md по своей природе затрагивает
и бэкенд, и панель одновременно (например T3.6 — сквозной сценарий), и должна
откатываться одним действием.

## Решение

Один репозиторий разработки (монорепо) в корне проекта. Вся история, все коммиты и
весь CI — здесь. Наружу отдаются зеркала поддеревьев:

```
make publish-backend   → git subtree push --prefix=backend <remote> main
make publish-panel     → git subtree push --prefix=panel   <remote> main
make publish-widget    → git subtree push --prefix=widget  <remote> main
```

Адреса внешних репозиториев задаются в `.env` (не в Makefile), чтобы их отсутствие
не ломало сборку у того, кому публикация не нужна.

Разграничение ответственности — через `CODEOWNERS` и branch protection: правка
`backend/**` требует ревью владельца бэкенда, `panel/**` — владельца панели.
Разные деплои — через отдельные Dockerfile и фильтр по путям в CI
(`paths: ['backend/**']`), а не через разделение репозиториев.

## Альтернативы и почему отвергнуты

- **Два независимых репозитория в подкаталогах (вариант A).** Даёт настоящую изоляцию
  доступов, но оставляет без версионирования корневые документы, compose, Makefile и
  e2e — либо требует третьего репозитория для них. Коммит по кросс-компонентной задаче
  перестаёт быть атомарным: два коммита, два push, откат руками в двух местах.
- **Мета-репозиторий с submodules (вариант B).** Фиксирует версии компонентов, но
  добавляет постоянную ручную работу: detached HEAD, два коммита на изменение,
  `--recurse-submodules`, пустые каталоги у того, кто забыл флаг. Для трёх компонентов
  цена выше пользы.
- **Монорепо без публикации вообще.** Проще всего, но не выполняет внешнее требование
  «два репозитория».

## Последствия

- Атомарные коммиты по задачам из tasklist.md сохраняются; один `git revert` откатывает
  задачу целиком, включая миграцию, API и UI.
- Внешние репозитории **read-only**: принимать в них PR нельзя, правки идут только из
  монорепо и доезжают следующей публикацией. Это ограничение, а не недоработка.
- Монорепо **не изолирует доступ к чтению**: все, у кого есть доступ к репозиторию,
  видят весь код. Если понадобится реально закрыть одну часть от других участников,
  решение пересматривается и выполняется `git subtree split` — он работает и на
  накопленной истории, то есть переход к варианту A остаётся дешёвым.
- `git subtree push` переписывает историю поддерева при каждой публикации и работает
  тем медленнее, чем длиннее история; при заметном замедлении переходим на
  зеркалирование из CI.
