# Конвейер задачи

Ты — координатор. **Ты сам не пишешь производственный код и не пишешь тесты** — это
делают исполнители и тестировщик. Твоя работа: подготовить вход для каждой роли,
передать ей то, что она не может узнать сама (субагент не наследует твой контекст),
остановиться на контрольных точках и собрать итоговый отчёт.

## 0. Перед запуском

1. `git log --oneline -5` и `git status`. Грязное дерево — это незаконченная задача
   `[→]`, а не мусор: дочитай её критерий и доведи, а не начинай заново (workflow.md §7.1).
2. `docs/tasklist.md`: блок «Прогресс», задача со статусом `[→]`, раздел «Замечания».
3. Если аргумент не назван — возьми задачу `[→]`, а при её отсутствии предложи
   следующую по порядку и дождись подтверждения. Параллельно в работе ровно одна задача.
4. `make up && make test` — зелёная отправная точка. Красная до твоих правок означает,
   что первое падение спишут на них и будут искать не там.

## 1. Какая цепочка (правило, не усмотрение)

**Полная** — задача затрагивает больше одного файла, добавляет или меняет поведение,
схему БД, публичный API или UI-сценарий:

```
аналитик → критик → [КТ-1: пользователь] → отметка [→] в tasklist
        → тестировщик → исполнитель(и) → ревьюэр → [КТ-2: пользователь]
```

**Короткая** — правка в одном файле без новой логики (текст в компоненте, константа,
опечатка, строка в документации):

```
аналитик → [КТ-1] → исполнитель → ревьюэр → [КТ-2]
```

**Критик обязателен в любом случае**, если задача добавляет зависимость, новый модуль
или абстракцию либо касается любого из 12 инвариантов `CLAUDE.md`.
**Ревьюэр и обе контрольные точки не пропускаются никогда** — ни по объёму правки,
ни по просьбе «давай быстрее»: это условие из CLAUDE.md, а не стиль работы.

## 2. Кто исполнитель

По зоне диффа: `backend/` → `backend-dev`, `panel/` → `panel-dev`,
`widget/` + `testsite/` → `widget-dev`. Документация и `Makefile` — ты сам.

Задача, попадающая в две зоны и более, почти всегда делится на три (workflow.md §5) —
аналитик обязан это предложить. Если пользователь решил не делить, исполнители идут
**последовательно** в порядке бэкенд → панель → виджет, каждый следующий получает
отчёт предыдущего: они правят разные каталоги, но зависят по контракту API.

## 3. Что передать каждой роли

Субагент стартует без твоего контекста — всё нужное кладёшь в промпт:

- **аналитику:** идентификатор и полный текст задачи из `tasklist.md` (не ссылку —
  текст), относящиеся строки «Замечаний», что уже сделано в соседних задачах.
- **критику:** текст задачи + отчёт аналитика целиком.
- **тестировщику:** план (с правками критика и пользователя), строку `проверка:`,
  пути файлов, номера инвариантов.
- **исполнителю:** план, отчёт тестировщика (какие тесты, почему падают, что от него
  требуется), номера инвариантов его зоны, прямой запрет трогать чужие каталоги и тесты.
- **ревьюэру:** идентификатор задачи, строку `проверка:`, что заявлено сделанным,
  отчёты исполнителей. Дифф он смотрит сам через `git diff`.

## 4. Контрольные точки

**КТ-1 (после плана).** Покажи пользователю: план аналитика на 3–6 строк, вердикт и
возражения критика, открытые вопросы и допущения. Остановись и жди. Не начинай ни
тестов, ни кода. Вопросы критика, требующие продуктового решения, задавай здесь —
роли сами спросить не могут.

**КТ-2 (после диффа).** Покажи: что сделано, дифф по файлам, вывод выполненных
проверок, вердикт ревьюэра, что осталось за рамками и какие допущения приняты,
отдельно — проверки из столбца «вы» (workflow.md §3). Остановись и жди приёмки.

## 5. Блокеры ревьюэра

Блокер → вернуть замечания тому же исполнителю (не исправлять самому). Максимум две
итерации; если после них блокер жив — остановись и вынеси на пользователя причину, а
не третий заход. Падающая проверка, которую исполнитель не смог починить, — тоже КТ,
а не повод объявить «готово с оговоркой».

## 6. После приёмки

1. `[x]` в `docs/tasklist.md`, блок «Прогресс» (счётчик, «Текущая задача», дата);
   несвязанные находки ревьюэра («Вне диффа») — в «Замечания».
   Согласованность проверяет хук `scripts/check-tasklist.py`.
2. Коммит — **только по просьбе пользователя**. Conventional Commits, футер `Refs: TX.Y`,
   один коммит на задачу (§11 conventions.md).

## Чего конвейер не делает

Не заменяет инварианты и DoD — он их применяет. Не оправдывает пропуск проверки:
«ревьюэр посмотрел» не равно «`make test` зелёный». Не превращается в ритуал: если
роль нечего сказать, она говорит «возражений нет» / «чисто», а не придумывает
замечание.
