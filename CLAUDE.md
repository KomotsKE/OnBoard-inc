# OnBoard — правила проекта

Платформа интерактивного онбординга: встраиваемый JS-виджет для сайтов клиентов +
личный кабинет для сборки туров и аналитики.

Репозиторий один; `backend/`, `panel/` и `widget/` публикуются наружу как зеркала
поддеревьев ([ADR-0007](docs/adr/0007-monorepo-with-subtree-publishing.md)). Коммит
по задаче может затрагивать несколько компонентов — так и задумано.

**Начало работы или возобновление после обрыва:** последовательность из пяти шагов —
§7.1 [docs/workflow.md](docs/workflow.md). Коротко: `git log` и `git status`, затем
`docs/tasklist.md` (блок «Прогресс», задача со статусом `[→]`, «Замечания»), затем
`make up && make test` для зелёной отправной точки. Задача берётся в работу отметкой
`[→]` до начала кода; одновременно в работе одна. Перед кодом — `docs/conventions.md`.

## Порядок работы над задачей

```
план (3–6 строк) → ваше подтверждение → тест → код → запуск проверки
   → дифф и отчёт → ваша приёмка → отметка в tasklist.md → коммит по просьбе
```

Коммиты — **Conventional Commits**: `feat(backend): аутентификация по JWT`, ссылка на
задачу футером `Refs: T1.2`. Проверяется хуком `commit-msg` и в CI; типы и скоупы —
§11 [docs/conventions.md](docs/conventions.md).

Контрольные точки обязательны: после плана и после диффа я останавливаюсь и жду
подтверждения. «Готово» не произносится, пока не выполнена команда из строки
`проверка:` у задачи. Подробно — [docs/workflow.md](docs/workflow.md).

## Стек (зафиксирован)

Бэкенд: Python 3.12, FastAPI, **SQLAlchemy 2.0 async** (psycopg3), Alembic,
PostgreSQL 16 ([ADR-0010](docs/adr/0010-async-backend.md)).
Панель: React 18 + TypeScript, Vite, TanStack Query. Виджет: TypeScript, esbuild,
ноль рантайм-зависимостей. Тесты: pytest + httpx, vitest, Playwright.
Инфра: docker-compose + Makefile.

Разрешённые зависимости:

- бэкенд: `fastapi uvicorn sqlalchemy alembic psycopg[binary] pydantic-settings pyjwt
  argon2-cffi python-multipart httpx anyio` + dev: `pytest pytest-asyncio httpx ruff`;
- панель: `react react-dom react-router-dom @tanstack/react-query @dnd-kit/core
  @dnd-kit/sortable @dnd-kit/utilities` + dev: `typescript vite @vitejs/plugin-react vitest`;
- виджет: рантайм-зависимостей нет; dev: `typescript esbuild vitest jsdom` (проверка
  бюджета — свой `size.mjs` на `zlib`, пакет `size-limit` не понадобился);
- e2e: `@playwright/test`, `@axe-core/playwright` (проверка доступности, критерий T2.6);
- инструменты разработчика в корневом `.venv`: `pre-commit`.

Всё остальное — только после согласования.

```

make up / make down / make logs      docker-compose
```

Новая функциональность должна проверяться одной из этих команд. Нет команды — нет проверки.

## Инварианты (нарушение = блокер, не «доработаем потом»)

1. **Виджет не имеет права сломать сайт клиента.** Каждая публичная точка входа
   обёрнута в `try/catch`; ошибка гасится в `console.debug`. Необработанное исключение
   нашего кода на чужом сайте — инцидент у клиента.
2. **Не вмешиваемся в DOM и стили клиента.** Весь UI — в Shadow DOM под одним хостом
   в `<body>`; подсветка — SVG-маска. Чужие элементы, их классы, атрибуты и `z-index`
   не меняем. ([ADR-0002](docs/adr/0002-shadow-dom-ui.md), [ADR-0003](docs/adr/0003-svg-mask-highlight.md))
3. **Один глобал** — `window.OnBoard`. Встроенные объекты не патчим; исключение —
   обёртка над `history.pushState` для SPA, с вызовом оригинала.
4. **Изоляция арендаторов — в слое запроса.** `user_id` из JWT подставляется в SQL;
   чужой объект → **404**. ([ADR-0006](docs/adr/0006-tenant-isolation-404.md))
5. **Бюджет размера:** `loader.js` ≤ 5 КБ, `core.js` ≤ 30 КБ, `editor.js` ≤ 20 КБ gzip,
   проверяется `make size`. ([ADR-0001](docs/adr/0001-two-stage-widget-loading.md))
6. **Пользовательский текст — через `textContent`.** Никакого `innerHTML`.
7. **Без PII:** ни IP, ни email конечных пользователей, ни сырой User-Agent в БД.
8. **Ingest событий идемпотентен** по `event_id` (`ON CONFLICT DO NOTHING`).
9. **Схема БД — только через Alembic**, с рабочим `downgrade`.
10. **Без i18n:** интерфейс только русский, строки прямо в компонентах.
11. **Access-токен панели — только в памяти**, refresh — только в httpOnly cookie.
    В `localStorage` панели не хранится ничего, кроме UI-мелочей.
    ([ADR-0008](docs/adr/0008-session-storage.md))
12. **Готовность к росту без переписывания.** Ресурсы с пулами (`AsyncEngine`,
    `httpx.AsyncClient`) создаются один раз в `lifespan` с явными параметрами и
    таймаутами; состояние, живущее дольше запроса, не хранится в памяти процесса
    (только за интерфейсом, как `RateLimiter`); сетевых вызовов внутри открытой
    транзакции нет; event loop не блокируется (argon2 — в поток); списковые ответы —
    в конверте с пагинацией. Полный список — §12 [docs/conventions.md](docs/conventions.md).

## Как пишем код

Лучшие практики — не пожелание, а часть определения готовности:

- **KISS и YAGNI**: простейшее решение задачи; абстракция — со второго использования,
  параметр — со второго значения. Заготовок «на будущее» нет.
- **Обратимость вместо запаса прочности**: закладываем границы (пулы, таймауты,
  интерфейсы, конверты, идемпотентность), не строим механизмы без нагрузки. Вопрос
  для проверки: при росте нагрузки в 100 раз это переписывать или донастраивать?
- **DRY по правилу трёх**: дублирование убираем на третьем повторении, не на втором.
- **SOLID прагматично**: SRP и DIP соблюдаем всегда (сервис не знает про HTTP),
  остальное — только когда задача попросит. Интерфейс под одну реализацию запрещён.
- **Чистый код**: говорящие имена, функция ≈ до 30 строк, вложенность до 3 уровней,
  ранние возвраты, никаких магических чисел, мёртвый код удаляется, а не комментируется.
- **Комментарии объясняют «почему»**, со ссылкой на ADR, где решение неочевидно.
  Пересказ кода и закомментированный код — нет. `TODO` только со ссылкой на задачу.
- **README** в корне и в каждом компоненте (`backend/`, `panel/`, `widget/`,
  `testsite/`); правится в той же задаче, что изменила запуск или поведение.
- **Ошибки API** — по RFC 9457 (`application/problem+json`), свой формат не изобретаем.

Подробно и с примерами — §9 [docs/conventions.md](docs/conventions.md), чеклист перед
сдачей задачи — §10 там же.

## Деплой

Сейчас только локальный `docker-compose`, вынос на сервер — после приёмки MVP
(§15 [docs/vision.md](docs/vision.md)). Реальный CDN, TLS и CI не настраиваем;
адрес сервиса берётся из `.env`, чтобы переезд не требовал правок кода.

## Границы изменений

- Правим только то, что требует текущая задача. Соседний код, форматирование и
  комментарии не «улучшаем».
- Заметили несвязанную проблему — пишем в «Замечания» в `docs/tasklist.md`,
  не исправляем молча.
- Фичи сверх задачи не добавляем. Абстракции под одно использование не создаём.
- Архитектурное решение, которое дорого менять, оформляется записью в `docs/adr/`,
  а не правкой vision.md задним числом.
